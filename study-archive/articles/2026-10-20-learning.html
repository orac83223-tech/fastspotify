오늘의 중심 원자료와 읽을 범위

중심 원자료는 Malcolm Featonby의 AWS Builders’ Library 기술 글 Making retries safe with idempotent APIs입니다. 공개 페이지에서 별도 발표일을 확인하지 못해 날짜 미상으로 표시합니다. 실제 확인일은 2026-10-20 한국시간입니다. 오늘 읽을 범위는 Reducing client complexity, Retries and semantic equivalence, Late arriving requests, Same client request ID, different intent입니다. 중심 원자료

원자료의 핵심 설계는 호출자가 제공하는 요청 식별자로 중복 의도를 구분하고, 그 식별자 기록과 상태 변경을 원자적으로 묶는 것입니다. 같은 식별자로 다른 입력이 오거나 요청이 늦게 도착하는 경우도 계약에 포함합니다. 이는 실무 설계 설명이며 모든 시스템의 무고장 보장을 증명한 논문은 아닙니다. 이하 상태기계·확률 계산·장애 실험은 이 원칙을 이해하기 위해 구성한 교육용 모델입니다.

1. 선수개념: 멱등성, 안전성, 생존성은 각각 다르다

상태 x에 연산 f를 적용한다고 합시다. f(f(x)) = f(x)이면 f를 멱등이라고 부릅니다. 여기서 x는 저장된 업무 상태이고 f는 특정 입력으로 정의된 상태 변환입니다. 예를 들어 수량을 5로 설정하는 연산은 다른 변경이 끼어들지 않은 연속 적용에서는 멱등입니다. 반면 수량에 5를 더하는 연산은 두 번 적용하면 10이 늘어나므로 멱등이 아닙니다. 멱등이라는 말은 실행 코드가 한 번만 돌아간다는 뜻이 아닙니다.

안전성은 나쁜 일이 발생하지 않는다는 성질입니다. 하나의 신청으로 예약이 두 개 만들어지지 않는다는 규칙이 여기에 속합니다. 생존성은 좋은 일이 결국 발생한다는 성질입니다. 서버와 네트워크가 회복하고 요청이 계속 전달되면 신청이 결국 완료된다는 규칙입니다. 재시도를 전혀 하지 않으면 중복 가능성을 줄여도 필요한 신청을 영원히 놓칠 수 있습니다. 반대로 무한히 재시도해도 서버가 영원히 복구되지 않는 상황에서는 완료를 보장할 수 없습니다.

HTTP에서도 안전한 메서드와 멱등 메서드를 구분합니다. 읽기 중심의 안전성은 요청한 의미가 서버 상태 변경을 요구하지 않는다는 뜻이고, 멱등성은 반복 요청의 의도된 효과에 관한 성질입니다. 2022년 6월 RFC 9110 §9.2.2는 PUT과 DELETE 및 안전한 메서드를 멱등으로 정의합니다. 응답 코드나 부수적인 로그까지 매번 같아야 한다는 뜻은 아닙니다. POST라는 이름만 보고 안전한 재시도를 가정해서도 안 됩니다. HTTP Semantics

여기에 함정이 하나 더 있습니다. 설정 연산이 멱등이어도 오래 지연된 요청이 최신 값을 덮어쓰는 문제는 남습니다. 값을 5로 설정한 뒤 다른 요청이 8로 바꿨는데 첫 요청의 복사본이 늦게 도착하면 최종값이 5가 됩니다. 따라서 중복 제거와 요청 간 순서 보장은 별도의 문제입니다. 한 작업을 식별하는 키와 객체의 현재 버전을 식별하는 번호를 혼동하면 안 됩니다.

05

2. 타임아웃을 실패라고 쓰면 논리가 무너진다

가상의 도서관 좌석 예약 서비스를 생각해 봅시다. 클라이언트가 좌석 하나를 예약해 달라고 요청하고 2초 동안 응답을 기다립니다. 요청이 서버에 도착하기 전에 끊겼을 수도 있고, 예약을 저장한 다음 응답 패킷만 사라졌을 수도 있습니다. 두 상황에서 클라이언트 화면은 똑같이 타임아웃입니다. 관측이 같다는 이유로 실제 상태도 같다고 판단할 수는 없습니다.

이 구분은 MIT의 2026년 Threads and RPC 강의에서도 다룹니다. RPC 호출 실패는 요청 미도착, 실행 후 서버 장애, 응답 경로 장애 등을 구분해 주지 않습니다. 오늘 예제에서는 이 사실을 이용해 타임아웃을 실패 상태가 아니라 결과 미확인 상태로 둡니다. 미확인 상태는 불편하지만 정확합니다. 실제로 끝난 작업을 실패로 선언한 뒤 새 신청을 만드는 것이 더 위험합니다. MIT RPC 강의노트

클라이언트의 상태를 NEW, WAITING, UNKNOWN, SUCCEEDED, REJECTED로 나누겠습니다. NEW는 아직 발송하지 않은 상태, WAITING은 응답을 기다리는 상태, UNKNOWN은 결과를 모르는 상태, SUCCEEDED는 확인된 완료, REJECTED는 규칙에 따라 명확하게 거절된 상태입니다. UNKNOWN에서 복구할 때는 동일한 논리적 작업으로 재질의하거나 같은 키로 재시도해야 합니다. 새로운 키를 만들면 서버에는 새 업무로 보입니다.

REJECTED도 단순한 네트워크 오류와 다릅니다. 좌석이 없다는 확정 응답을 받은 신청을 나중에 다른 좌석 조건으로 다시 내는 것은 새로운 의도입니다. 서버의 응답은 상태뿐 아니라 어떤 입력에 대한 결정인지를 연결해야 합니다. 또한 조회가 일시적으로 아무 결과도 돌려주지 않았다는 것만으로 미실행을 확정해서는 안 됩니다. 오래된 복제본에서 읽었다면 이미 커밋된 예약을 못 볼 수 있기 때문입니다.

06

3. 요청 키는 데이터의 지문이 아니라 의도의 이름이다

예약 요청을 r = (u, k, p)로 쓰겠습니다. u는 인증된 호출 주체의 식별자, k는 그 주체가 부여한 논리적 작업 키, p는 좌석·시간대 등 입력 묶음입니다. 서버는 (u, k)를 중복 판단의 기본 범위로 사용합니다. p의 정규화된 표현을 h(p)라는 지문으로 저장할 수 있는데, h는 입력 비교를 위한 해시 함수입니다. 이때 해시 충돌을 무시할 수 있을 만큼 적절한 함수를 선택하거나 중요한 필드를 직접 함께 비교한다는 가정이 필요합니다.

같은 사람이 같은 시간대에 같은 크기의 회의실 두 개를 실제로 원할 수도 있습니다. 따라서 입력 p가 같다는 이유만으로 한 신청으로 합치면 정상 업무를 지워 버립니다. 반대로 동일 신청을 재전송하면서 k를 바꾸면 같은 p라도 중복 실행을 막지 못합니다. 업무의 동일성은 데이터 모양만으로 완전히 추론할 수 없으므로 호출자와 서버가 키의 의미를 합의해야 합니다.

동일한 (u, k)에 h(p)가 다르면 조용히 최신 입력으로 덮어쓰지 않고 충돌로 처리하는 것이 이 예제의 정책입니다. 처음에는 오전 좌석을 신청하고 다음에는 오후 좌석으로 바꿨는데 같은 키를 붙였다면 어느 요청이 진짜 의도인지 서버가 대신 추측하지 않는 것입니다. 사용자에게 입력을 수정한 새 신청임을 명시하게 하거나, 별도의 변경 연산으로 연결해야 합니다.

키의 범위도 계약입니다. 생성 API와 취소 API가 같은 키 공간을 공유할지, 작업 종류를 복합키에 포함할지 정해야 합니다. 여기서는 예약 생성 전용 키 공간이라고 가정합니다. 키는 인증 수단이 아닙니다. 다른 호출자가 남의 키를 알아도 결과를 읽거나 작업을 재실행할 수 없도록 먼저 권한을 검사해야 합니다. 무작위 식별자가 길다는 사실과 접근 통제가 있다는 사실은 별개입니다.

07

4. 경쟁하는 두 요청을 하나의 커밋으로 모으기

서버에는 예약 테이블과 처리 결과 테이블이 있다고 합시다. 결과 테이블의 기본키는 (u, k)이며 입력 지문, 결정 결과, 예약 식별자를 담습니다. 교육용 구현은 두 테이블을 같은 ACID 데이터베이스에 저장합니다. 같은 트랜잭션에서 결과 키를 선점하고 예약을 만들고 결과를 기록한 뒤 커밋합니다. 여기서 원자성은 셋 중 일부만 영구적으로 남지 않는다는 조건입니다.

의사코드 1단계: 인증과 입력 형식 검사를 한 뒤 트랜잭션을 시작합니다. (u, k)를 유일 키로 새 처리 기록을 삽입하려고 시도합니다. 단순히 먼저 SELECT하여 없음을 확인한 뒤 독립적으로 INSERT하는 패턴이 아니라 데이터베이스의 유일성 제약을 최종 판정자로 사용합니다. 이 코드는 설명용이며 실제 DB의 충돌 처리와 격리수준에 맞춰 구현해야 합니다.

의사코드 2단계: 키를 확보한 트랜잭션만 예약 가능 조건을 확인하고 예약 레코드와 확정 결과를 저장합니다. 조건부 수량 감소나 잠금 등으로 좌석 초과 예약도 따로 막습니다. 중복 키 제거는 다른 키 두 개가 마지막 좌석을 동시에 차지하는 문제까지 해결하지 않습니다. 이는 이전 SSI 글에서 배운 업무 불변식과 연결됩니다.

의사코드 3단계: 커밋 성공 뒤 결과를 반환합니다. 같은 키의 다른 요청이 이미 커밋된 기록과 충돌했다면 입력 지문을 비교하고 기존 결과를 읽어 반환합니다. 다른 트랜잭션이 아직 진행 중이면 기다리거나 재조회 가능한 진행 중 응답을 보냅니다. 충돌을 발견했다고 무조건 성공으로 간주하지 않습니다. 원래 트랜잭션이 롤백했을 수도 있기 때문입니다.

왜 이것이 안전한지 작은 증명을 해 봅시다. 하나의 (u, k)에 대해 두 개의 확정 예약이 생겼다고 가정합니다. 각 예약 생성은 같은 트랜잭션에서 그 키를 새로 삽입하는 데 성공해야 합니다. 그러나 커밋된 키가 보존되고 유일성 제약이 올바르게 작동하면 두 삽입이 모두 새 기록으로 커밋될 수 없습니다. 따라서 두 예약이 생긴다는 가정과 모순입니다. 이 논증은 외부 예약 시스템을 호출하지 않고 같은 DB에서 효과를 확정한다는 전제에 의존합니다.

키 기록 후 죽으면 예약이 없는데 완료로 보일 수 있고, 예약 후 키 기록 전에 죽으면 재시도 때 또 예약할 수 있습니다. 그러므로 두 단계를 다른 커밋으로 분리하는 순간 증명의 전제가 사라집니다. 메모리의 잠금만으로도 부족합니다. 프로세스가 재시작하거나 여러 서버가 동시에 요청을 받으면 공통의 영속 판정점이 필요합니다. 다만 모든 요청을 하나의 전역 잠금에 묶으라는 뜻은 아닙니다. 충돌하는 키와 좌석에 필요한 범위만 직렬화할 수 있습니다.

08

5. 손계산: 작은 응답 유실률이 만드는 중복 수

다음은 실측이 아닌 교육용 확률 모델입니다. 최초 요청 N = 10,000개가 모두 서버에서 성공했고, 그 성공 응답만 독립적으로 q = 0.02의 확률로 사라진다고 가정합니다. 각 클라이언트는 응답을 못 받으면 정확히 한 번 재시도하며 재시도 요청은 모두 서버에 도달하고 성공합니다. N은 논리적 작업 수, q는 첫 성공 응답의 유실 확률입니다.

중복 제거가 없으면 중복 효과 수 D의 기댓값은 E[D] = Nq = 200개입니다. 서버의 효과 실행 총수의 기댓값은 N + E[D] = 10,200개입니다. 이 모델에서 정상 업무는 10,000개이므로 재시도로 늘어난 200개는 가용성 개선이 아니라 이미 끝난 작업의 추가 실행입니다. 중복 키 계약이 정확히 작동하면 네트워크 요청 수는 여전히 평균 10,200회지만 예약 효과는 10,000개로 제한됩니다.

재시도를 무한히 허용하고 매번 응답이 독립적으로 q의 확률로 사라지는 다른 모델도 생각할 수 있습니다. q가 1보다 작고 매 요청이 실제로 처리된다면 첫 응답을 받을 때까지 시도 수 A의 기댓값은 E[A] = 1/(1−q)입니다. q = 0.02이면 약 1.020408회입니다. 중복 방지가 없다면 작업 하나당 불필요한 효과의 기댓값은 q/(1−q), 약 0.020408개입니다. 앞 모델의 0.02와 다른 이유는 두 번째 이후 응답 유실도 허용했기 때문입니다.

현실의 장애는 독립적이지 않습니다. 서버 과부하가 원인이라면 실패한 요청들이 동시에 재시도하여 q 자체를 높일 수 있습니다. 따라서 위 숫자를 서비스 장애 예측치로 쓰면 안 됩니다. 이 계산의 목적은 성공률이라는 숫자만 보고 재시도를 칭찬하지 말고 요청 수, 확정 효과 수, 응답 확인 수를 분리해 보자는 것입니다. 멱등성이 있어도 요청 처리·인증·조회 비용은 여전히 들기 때문에 재시도 폭주를 무해하다고 볼 수도 없습니다.

09

6. 처리 중 표시, 임대 시간, 오래된 작업자의 귀환

예약이 짧은 DB 트랜잭션으로 끝나지 않고 보고서 생성처럼 수 분 걸린다면 앞 구현을 그대로 오래 붙잡아 두기 어렵습니다. 작업을 접수했다는 기록과 실제 실행을 나눌 수 있지만, 그러면 상태가 IN_PROGRESS에 남은 채 작업자가 죽는 문제를 새로 풀어야 합니다. 완료 기록이 없다는 이유만으로 다른 작업자가 무조건 같은 작업을 수행하면 중복 효과가 생길 수 있습니다.

교육용 상태기계에 작업 세대 번호 e를 추가해 봅시다. e는 작업 소유권이 새 작업자에게 넘어갈 때 증가하는 정수입니다. 작업자 A가 e = 7을 가지고 일하다가 오래 멈춘 사이 B가 e = 8을 받아 작업을 이어갑니다. 저장소가 현재 세대보다 작은 번호의 결과 쓰기를 거절한다면 뒤늦게 돌아온 A의 쓰기를 막을 수 있습니다. 이런 검사를 수행하는 번호를 흔히 fencing token이라고 부릅니다.

핵심은 번호를 발급했다는 사실이 아니라 실제 효과를 받는 쪽이 번호를 검사한다는 점입니다. A가 외부 시스템에 이미 요청을 보냈는데 그 시스템이 세대 번호도 중복 키도 검사하지 않으면 로컬 임대가 만료되었다고 외부 효과를 취소할 수 없습니다. 따라서 임대 시간만 짧게 정하면 정확성이 좋아진다는 주장은 성립하지 않습니다. 일시 정지한 프로세스는 죽은 프로세스와 다르게 다시 돌아올 수 있습니다.

이 절의 상태기계는 중심 원자료의 특정 구현을 재현한 것이 아닌 설계 사고 실험입니다. 빠른 로컬 트랜잭션과 장시간 외부 작업을 같은 코드 경로로 감추지 말자는 취지입니다. 후자의 완료 판단에는 외부 영수증, 작업 상태 조회, 같은 키를 지원하는 수신 API 또는 수동 대조 절차가 필요합니다. 그중 어느 것도 없으면 결과 미확인 상태를 유지하는 것이 정직한 설계입니다.

10

7. 멱등 기록은 언제 지워도 될까?

중복 키를 영원히 보관하면 저장 공간이 늘어납니다. 그러나 일정 시간이 지났다는 이유만으로 지우면 오래된 요청이 새 요청처럼 보일 수 있습니다. 교육용 계약에서 H는 최초 접수부터 모든 허용된 재시도와 지연된 요청이 마지막으로 도착할 수 있는 시간의 상한, R은 중복 기록 보존 시간이라고 정의합니다. 두 시간은 같은 접수 시점과 같은 시간 단위로 측정합니다. 안전한 삭제를 논하려면 적어도 R > H가 필요합니다.

예를 들어 클라이언트 재시도 허용 기간이 24시간이고 마지막 발송 요청이 최대 2시간 지연될 수 있다면 H = 26시간입니다. R을 30시간으로 정하면 이 가정 안에서는 4시간 여유가 있습니다. 반대로 장애 복구 과정에서 7일 뒤 오래된 큐를 재생하는 경로가 있다면 H = 26시간이라는 전제가 틀립니다. TTL 설정 하나보다 모든 재생 경로를 알아내는 일이 먼저입니다.

시간에는 또 다른 비용이 있습니다. 논리적 작업 도착률 λ를 초당 50개, 보존 시간 R을 30시간, 처리 기록 한 개의 크기 s를 200바이트라고 가정합시다. 정상상태 기록 수는 대략 λR = 50 × 108,000 = 5,400,000개이고, 원시 기록 용량은 B = λRs = 1,080,000,000바이트, 십진 단위 1.08GB입니다. R을 초로 변환했기 때문에 단위가 맞습니다. 인덱스·복제·트랜잭션 로그·저장 엔진의 여유 공간은 제외한 하한 성격의 계산입니다.

무한히 늦은 재전송을 허용하면서 유한한 중복 기록만 유지하면 과거 요청과 새 요청을 항상 구분할 수 없습니다. 오래된 키를 명시적으로 거절하는 기한 계약, 오래 유지되는 업무 식별자, 삭제 후에도 남는 최소 처리 흔적 가운데 무엇이 필요한지 결정해야 합니다. 삭제된 자원을 다시 만들고 싶다는 새 의도는 새 키로 표현하는 편이 명료합니다. 오래된 성공 결과는 당시 작업의 결과이지 그 자원이 지금도 존재한다는 보장이 아닙니다.

11

8. 정확히 한 번이라는 보장은 어디까지 이어질까?

이제 예약을 저장하고 알림까지 보내야 한다고 합시다. DB 커밋 후 알림을 보내기 전에 죽으면 예약은 생겼지만 알림은 없습니다. 알림을 먼저 보내고 DB 커밋 전에 죽으면 예약되지 않았다는 알림을 보낼 수도 있습니다. 순서를 바꾸는 것만으로 두 시스템을 하나의 원자적 작업으로 만들 수 없습니다.

교육용 개선안은 예약과 발송 의도를 같은 DB 트랜잭션에 기록하는 것입니다. 별도 전달자는 미전달 의도를 읽어 알림 시스템에 넘깁니다. 이 구조는 커밋된 예약의 발송 의도가 사라지는 문제를 줄이지만, 알림 수신 직후 전달자가 죽으면 같은 의도를 다시 보낼 수 있습니다. 따라서 수신자가 의도 식별자로 중복 효과를 제거해야 마지막 단계까지 안전해집니다. 이것이 transactional outbox를 사용해도 수신 측 계약을 생략할 수 없는 이유입니다.

Kafka 4.1 공식 설계 문서는 Kafka 토픽 사이에서 출력과 소비 위치를 같은 트랜잭션으로 확정할 수 있다고 설명합니다. 그러나 외부 목적지의 정확히 한 번 처리는 그 목적지와의 협력이 필요하다고 구분합니다. 이것은 현재 문서에서 확인한 보장 범위이며 모든 외부 부작용에 자동 적용되는 기능이라는 뜻이 아닙니다. Kafka Message Delivery Semantics

예를 들어 소비 위치는 “여기까지 읽었다”는 번호이고 외부 예약은 “현실에 무엇을 남겼다”는 효과입니다. 번호만 먼저 저장하면 실제 효과를 놓칠 수 있고 효과만 먼저 저장하면 재시작 후 다시 만들 수 있습니다. 두 값을 같은 원자적 경계에서 갱신하거나 효과를 받는 쪽에서 안정된 키로 중복을 막아야 합니다. 이처럼 시스템 경계를 하나 넘을 때마다 보장도 다시 검토해야 합니다.

2022년 이후 흐름과 연결할 때도 새로운 마케팅 용어보다 계약의 구체화를 보는 편이 유용합니다. RFC 9110은 HTTP 메서드 의미를 명문화했고, 2026년 MIT 강의는 여전히 불확실한 RPC 결과를 핵심 문제로 가르칩니다. 버전이 명시된 Kafka 문서에서는 트랜잭션의 내부 범위와 외부 협력 조건을 구분해 읽을 수 있습니다. 최근 문서에 실렸다는 사실과 그 원리가 최근에 발명됐다는 주장은 다릅니다. 오늘의 개념은 오래된 분산 시스템 문제를 현재의 실행 경계에 적용하는 방법입니다.

9. 가장 강한 반론과 검증 실험

강한 반론은 멱등 결과 테이블이 또 하나의 병목과 장애 지점을 만든다는 것입니다. 맞습니다. 모든 읽기 요청에 영구 기록을 남기는 것은 비싸며, 근사 집계에서 아주 작은 중복을 허용하는 편이 합리적일 수 있습니다. 반대로 한 번의 중복이 되돌릴 수 없는 효과를 남기는 작업에서는 기록 비용이 작아 보일 수 있습니다. 중요한 것은 모든 API에 같은 장치를 붙이는 것이 아니라 어떤 효과를 어느 기간까지 한 번으로 제한할지 명시하는 일입니다.

검증 실험도 응답 성공률만 보지 않아야 합니다. 동일 키를 여러 연결에서 동시에 보내고, 커밋 직전과 직후에 서버를 종료하고, 응답만 버리고, 키 보존 기한 이후 오래된 요청을 재생해 봅니다. 각 시험에서 클라이언트가 받은 응답, 확정된 예약 수, 중복 기록의 입력 지문과 결과를 함께 대조합니다. 한 연결에서 순서대로 두 번 호출한 시험만 통과해서는 동시성 계약을 확인한 것이 아닙니다.

서로 다른 키 두 개로 마지막 좌석을 경쟁시키는 시험도 별도로 필요합니다. 동일 키 중복은 없는데 좌석 수를 초과했다면 멱등 처리와 업무 불변식 중 후자가 깨진 것입니다. 반대로 좌석 수는 맞지만 서로 다른 두 의도를 한 키로 합쳐 버렸다면 계약의 식별 방식이 틀린 것입니다. 최종 숫자가 우연히 맞는 것만으로 정확성을 주장하지 말고 각 논리적 작업에 결과가 어떻게 대응되는지 봐야 합니다.

테스트가 모든 장애 순서를 증명하지는 않습니다. 그래서 앞의 짧은 안전성 논증과 장애 주입을 함께 사용합니다. 논증은 필요한 전제를 드러내고, 시험은 실제 구현이 그 전제를 어기는 지점을 찾습니다. 배포 뒤에는 응답 지연뿐 아니라 중복 키 재사용률, 다른 입력 충돌 수, 미확인 작업의 체류 시간, 기록 만료 뒤 재도착 수를 관측하면 계약을 현실적인 방향으로 조정할 수 있습니다. 이 항목들은 작성자의 일반적인 검증 제안이지 특정 제품의 실측 결과가 아닙니다.

10. 확인 문제를 풀기 전에 남길 결론

재시도는 실패를 지우는 장치가 아닙니다. 결과를 모르는 상태에서 같은 의도를 다시 전달하는 장치입니다. 따라서 의도의 이름을 유지하고, 중복 판정과 효과를 같은 확정 경계에 넣고, 그 경계 밖으로 나간 효과는 별도 계약으로 연결해야 합니다. 정확히 한 번이라는 문장을 만나면 “무엇이, 어떤 장애를 가정하고, 어느 시스템까지, 얼마 동안인가”를 먼저 물어야 합니다.

아래 확인 문제는 먼저 종이에 풀어 보세요. 첫 문제는 확률 계산, 둘째는 원자성 반례, 셋째는 보존 기한과 외부 효과의 경계를 확인합니다. 해설은 문제 아래 별도로 열어 볼 수 있습니다. 계산 결과보다 어떤 가정을 추가해야 결론이 성립하는지 설명하는 데 시간을 쓰는 것이 좋습니다.

Q1. 최초 요청 5,000개가 모두 실제 처리되었고 첫 성공 응답의 유실 확률은 3%다. 응답을 못 받은 요청은 한 번만 재시도하며 그 재시도는 모두 처리된다. 중복 제거가 없을 때 중복 효과와 전체 효과 수의 기댓값은? 정확한 중복 제거가 있으면 무엇이 달라지는가?해설 보기 +

중복 효과의 기댓값은 5,000 × 0.03 = 150개, 전체 효과는 5,150개다. 정확한 중복 제거가 있으면 업무 효과는 5,000개이며 요청 수의 기댓값 5,150회는 그대로다. 첫 요청 자체의 실패 확률을 가정하지 않았으므로 성공확률을 다시 계산하는 문제와 구별해야 한다.

Q2. 서버가 처리 키를 먼저 커밋한 다음 예약을 별도 트랜잭션으로 저장한다. 두 단계 사이에 서버가 종료되면 어떤 일이 생기는가? 순서를 거꾸로 하면 안전한가?해설 보기 +

키만 남고 예약은 없을 수 있다. 재시도가 키만 보고 완료로 판단하면 필요한 예약을 영원히 놓친다. 예약부터 커밋하면 예약만 남은 뒤 키가 없어서 재시도가 예약을 또 만들 수 있다. 두 기록을 같은 원자적 트랜잭션으로 묶거나, 분리된 상태를 정확히 복구하는 더 강한 프로토콜이 필요하다. 단순 순서 변경은 해결책이 아니다.

Q3. 클라이언트 재시도 기한 24시간, 마지막 요청의 최대 지연 2시간, 키 보존 30시간이면 예제의 시간 조건은 맞는가? 7일 뒤 큐 재생과 중복 키를 받지 않는 외부 알림 시스템이 추가되면 어떤 결론을 수정해야 하는가?해설 보기 +

주어진 첫 가정에서는 H = 26시간이고 R = 30시간이므로 R > H다. 그러나 7일 뒤 재생 경로를 허용하면 H의 기존 상한이 틀려 30시간 보존으로 전체 중복 방지를 보장할 수 없다. 외부 알림은 로컬 예약·의도 기록과 원자적 경계를 공유하지 않으므로 수신 측 중복 제거 또는 확인 가능한 외부 결과 계약이 별도로 필요하다. outbox만으로 알림 효과가 정확히 한 번이라고 결론내릴 수 없다.
