02

오늘의 질문: AI 에이전트 시대에는 왜 ‘가장 한가한 GPU’로 보내면 안 될까?

오늘 비교한 세 후보는 ① 에이전트 워크로드가 기존 LLM 로드밸런싱을 왜 깨뜨리는가, ② 긴 컨텍스트에서 KV cache가 HBM·네트워크·스토리지 설계를 어떻게 바꾸는가, ③ prefill/decode 분리가 GPU 클러스터의 새로운 기본 구조가 될 수 있는가였습니다. 최근에는 장기기억·온톨로지·AI 코드 검증을 다뤘기 때문에, 오늘은 그 위에서 실제 에이전트 요청이 데이터센터 안을 어떻게 이동해야 하는지를 골랐습니다.

핵심 통찰은 이렇습니다. 전통적인 로드밸런서는 ‘가장 한가한 서버’를 찾지만, AI 에이전트 시대의 좋은 라우터는 ‘이미 이 요청의 과거를 기억하고 있는 서버’를 먼저 찾고, 그 서버가 너무 바쁠 때만 다른 곳으로 보냅니다. 이유는 KV cache 때문입니다. 같은 대화를 다른 GPU로 보내면 계산 능력은 남아 있어도 이미 계산해 둔 긴 문맥을 잃고 다시 prefill해야 합니다. 따라서 최적 라우팅의 목적함수는 단순 GPU utilization이 아니라 cache locality + token load + latency SLO의 결합으로 바뀝니다.

03

1. 기존 로드밸런싱의 암묵적 가정이 에이전트에서 깨진다

웹 서버의 전형적인 요청은 비교적 독립적입니다. 로그인 요청 A를 서버 1이 처리했다고 해서 다음 이미지 요청 B도 반드시 서버 1이 처리할 이유는 없습니다. 그래서 round-robin, least-connections, least-load 같은 정책이 잘 작동합니다.

그런데 LLM 에이전트는 다릅니다. 한 세션이 수십 번, 수백 번 이어지고 매 턴마다 이전 대화·system prompt·도구 결과·문서가 다시 들어갑니다. 2026년 8월 AI Engineer 행사에서 Red Hat의 Yuchen Fama와 Ashish Kamra는 자사에서 관찰한 agentic trace가 짧은 대화부터 3,000턴까지 이어지고, 일부 패턴에서는 KV-cache hit rate가 90%를 넘으며 input/output token 비율이 100:1을 넘기도 한다고 소개했습니다. 이 수치는 특정 워크로드의 발표 사례이므로 산업 평균으로 확대하면 안 되지만, agent traffic이 ‘독립 요청들의 평균’이 아니라 ‘긴 상태를 공유하는 변동성 높은 세션’이라는 점을 잘 보여줍니다. (유튜브) AI Engineer 공식 영상 열기

이 차이는 분산시스템에서 stateless request와 stateful session의 차이와 같습니다. 웹 시대에는 상태를 서버 밖 DB나 Redis에 두고 애플리케이션 서버를 stateless하게 만드는 것이 확장성에 유리했습니다. 하지만 LLM inference에서는 KV cache를 매 요청마다 다른 노드로 옮기거나 다시 계산하는 비용이 커질 수 있습니다. 그래서 완전한 statelessness가 오히려 비싸질 수 있습니다.

04

2. KV cache는 ‘이미 지불한 계산’을 저장한 자산이다

Transformer가 긴 prompt를 처음 읽는 prefill 단계에서는 각 token의 Key와 Value tensor를 계산합니다. 이후 autoregressive decode에서는 이전 token의 K/V를 매번 다시 계산하는 대신 KV cache에서 읽습니다.

vLLM의 Automatic Prefix Caching도 같은 아이디어입니다. 이미 처리한 prefix의 KV block을 hash 기반으로 찾아 재사용하면 같은 긴 system prompt나 문서를 다시 계산하지 않아도 됩니다. vLLM 문서는 이를 동일 prefix에 대한 중복 prompt 계산을 피하는 핵심 최적화로 설명합니다. (vLLM) vLLM Automatic Prefix Caching 문서

이를 경제적으로 보면 KV cache는 이미 지불한 계산비용을 미래 요청에서 재사용할 수 있게 하는 자산입니다.

Claude Sonnet 4.6의 2026년 5월 공식 API 가격표를 예로 들면 표준 input token은 100만 token당 3달러, cache hit는 0.30달러였습니다. API 가격이 하드웨어 원가와 동일하다는 뜻은 아니지만, 공급자가 cache reuse에 큰 경제적 가치를 부여한다는 신호로는 볼 수 있습니다. (Anthropic)

05

3. 그래서 ‘가장 한가한 GPU’가 오히려 느릴 수 있다

단순한 예를 들어보겠습니다.

GPU A는 현재 80% 부하지만 필요한 KV cache를 이미 갖고 있고, GPU B는 20% 부하지만 cache가 없다고 합시다. A의 queue wait가 0.5초이고 cache hit 처리시간이 1초라면 총 1.5초입니다. B는 queue wait가 0.1초뿐이어도 긴 prefix를 다시 prefill하는 데 3초가 걸린다면 총 3.1초입니다.

전통적인 least-load는 B를 선택하지만 실제 사용자는 A가 더 빠릅니다.

반대로 A의 queue wait가 2.5초로 늘어나면 A의 총시간은 3.5초가 되어 이제 B가 더 낫습니다. 즉 정답은 “항상 cache가 있는 서버로 보내라”도 아닙니다.

cache locality의 가치와 queueing delay를 매 순간 비교해야 합니다.

2026년 8월 llm-d 프로젝트가 공개한 표현이 정확합니다. Sticky Until Saturated. prefix가 이미 있는 endpoint를 우선하되 그 endpoint가 포화 임계점을 넘으면 affinity를 버리고 load 기준으로 다른 곳을 선택합니다. llm-d는 이 정책을 token-aware routing으로 설명하며, prefill-bound workload와 decode-bound workload에 서로 다른 부하 신호를 사용합니다. (Llm-D) llm-d — Sticky Until Saturated

06

4. 요청 개수 자체가 잘못된 부하 지표일 수 있다

전통적인 로드밸런서는 “서버 A에 요청 10개, 서버 B에 5개”를 보고 B가 더 한가하다고 판단할 수 있습니다.

하지만 LLM 요청에서는 요청 하나의 크기가 너무 다릅니다. uncached prompt 200,000 token인 요청과 2,000 token인 요청은 둘 다 ‘요청 1개’지만 prefill 작업량은 약 100배 차이가 납니다.

그래서 llm-d의 precise prefix-cache routing은 각 pod의 KV-cache 상태를 추적하고, 필요한 prefix가 실제로 존재하는 endpoint를 우선한 뒤 그 안에서 token load가 낮은 곳을 고릅니다. 즉 request count보다 실제로 남아 있는 uncached work를 보려는 겁니다. (GitHub) llm-d Precise Prefix Cache Routing

이것은 운영체제 스케줄러와도 닮았습니다. 프로세스 개수만 세는 것보다 CPU burst, memory footprint, I/O wait를 구분해야 좋은 스케줄링이 가능하듯, AI inference도 request가 아니라 work의 양과 종류를 봐야 합니다.

07

5. Agent 시대에는 ‘data locality’가 다시 핵심 최적화가 된다

Hadoop 초기의 유명한 원칙은 “데이터를 계산으로 옮기지 말고 계산을 데이터가 있는 곳으로 보내라”였습니다.

KV-cache-aware routing도 본질적으로 같습니다.

요청을 KV cache가 있는 곳으로 보냅니다.

이것은 CPU cache locality, NUMA affinity, CDN edge caching, database buffer pool과 같은 오래된 시스템 원리의 반복입니다.

계산이 싸지고 데이터 이동이 비싸질수록 locality가 중요해집니다. AI에서 이 현상이 더 강한 이유는 KV cache가 단순 파일이 아니라 고대역폭 메모리 위에 있는 중간 계산 상태이기 때문입니다. cache miss가 발생하면 storage read 한 번으로 끝나는 것이 아니라 긴 prompt를 다시 transformer에 통과시켜야 할 수 있습니다.

그래서 긴 system prompt, codebase context, RAG 문서, tool trace가 반복되는 agent workload에서는 routing policy 자체가 inference optimization이 됩니다.

08

6. 그런데 prefill과 decode는 서로 원하는 GPU 사용법이 다르다

LLM inference는 크게 두 단계로 나뉩니다.

Prefill은 긴 input token을 병렬 처리해 KV cache를 만듭니다. 행렬연산 비중이 커 상대적으로 compute-bound입니다.

Decode는 새 token을 하나씩 생성하면서 model weight와 기존 KV cache를 반복해서 읽습니다. 특히 batch와 context가 커질수록 memory bandwidth와 latency가 중요합니다.

문제는 둘을 같은 GPU pool에서 처리하면 긴 prompt의 prefill이 latency-sensitive decode를 방해할 수 있다는 것입니다.

그래서 최근 serving architecture에서는 Prefill/Decode Disaggregation, 즉 PD 분리를 사용합니다. prefill 전용 worker와 decode 전용 worker를 나누고 prefill이 만든 KV cache를 decode worker로 넘깁니다.

NVIDIA Dynamo의 TensorRT-LLM backend도 disaggregated serving과 KV-cache transfer를 지원하며 NIXL/UCX 계열 전송 방식을 제공합니다. (NVIDIA Docs) NVIDIA Dynamo TensorRT-LLM 문서

09

7. 하지만 PD 분리는 공짜가 아니다 — 병목이 GPU에서 네트워크로 이동한다

prefill과 decode를 나누면 phase interference는 줄지만 KV cache를 노드 사이에서 전송해야 합니다.

즉,

GPU contention 감소 ↔ network traffic 증가

라는 교환이 생깁니다.

손익분기 조건은 개념적으로 다음처럼 생각할 수 있습니다.

Benefit(PD) > KV transfer cost + scheduling overhead + extra network latency

네트워크가 느리거나 KV cache가 매우 크면 분리한 이득보다 cache 이동비용이 커질 수 있습니다.

2026년 7월 공개된 SmartGen 논문도 self-hosted 환경에서 full KV-cache transfer가 inter-node network bandwidth를 포화시킬 수 있다는 문제에서 출발합니다. 저자들은 필요한 KV entry만 선택적으로 전송하는 구조를 제안했고, 실험에서 전량 전송 방식 대비 time-to-second-token을 최대 4.3배 줄였다고 보고했습니다. 아직 preprint이고 특정 실험환경 결과이므로 일반화에는 주의해야 합니다. (arXiv) SmartGen 논문

결국 “더 많은 GPU”가 아니라 GPU-HBM-NIC-network topology 전체를 하나의 시스템으로 봐야 합니다.

10

8. 가장 좋은 정책은 ‘cache hit 최대화’도 ‘균등 부하’도 아니다

cache hit rate를 100%에 가깝게 만드는 것이 항상 좋은 목표일까요?

아닙니다.

특정 대형 agent session의 cache가 GPU A에 있다는 이유로 모든 후속 요청을 A로 몰아주면 A가 hot spot이 되고 다른 GPU들은 놀 수 있습니다. 반대로 load balancing을 완전히 균등하게 하면 cache miss가 늘어 recomputation이 폭증합니다.

따라서 목적함수는 단일 KPI가 아니라 다음과 비슷합니다.

Score(worker) = α·CacheLocality − β·QueueDelay − γ·UncachedPrefillTokens − δ·KVTransferCost − ε·SLOViolationRisk

실제 llm-d가 이 수식을 그대로 쓰는 것은 아닙니다. 사고를 위한 모델입니다.

핵심은 local optimum을 피하는 것입니다. cache만 보면 hotspot이 생기고, load만 보면 cache를 버립니다. 이것은 투자에서도 익숙한 구조입니다. 수익률만 최대화하면 위험이 폭증하고, 위험만 최소화하면 수익 기회를 잃습니다. 시스템 설계도 결국 여러 비용함수의 균형 문제입니다.

11

9. 실무에서 중요한 KPI도 바뀐다

agent system에서는 단순 tokens/sec만으로 부족합니다. cache hit token ratio, uncached prefill tokens, TTFT, inter-token latency, P95/P99 latency, session별 eviction rate, worker별 KV utilization, KV transfer bytes, cache-hit와 miss 상태의 throughput을 함께 봐야 합니다.

특히 평균값이 위험합니다. agent traffic은 긴 세션, 짧은 세션, tool fan-out, 재시도, 긴 document context가 섞여 tail이 두껍습니다. 평균 latency가 괜찮아도 P99에서 대화가 끊기듯 느려질 수 있습니다.

그래서 capacity planning도 “평균 요청 100 QPS”보다 context length 분포와 cache reuse 분포를 보는 것이 중요해집니다. Red Hat 발표도 agent workload에서는 steady-state benchmark만으로는 실제 운영 특성을 놓칠 수 있다고 강조합니다. (유튜브)

12

10. 투자·전략 렌즈: AI inference의 해자는 GPU 개수보다 ‘state locality를 운영하는 소프트웨어’에도 생길 수 있다

AI 인프라를 GPU·HBM·광통신만으로 보면 물리적 병목은 잘 보이지만 software control plane의 경제적 가치가 빠질 수 있습니다.

agentic inference에서는 같은 hardware를 가지고도 어떤 request를 어느 pod로 보낼지, 어떤 KV를 HBM에 남길지, 무엇을 CPU·SSD로 내릴지, 언제 cache affinity를 깨뜨릴지, prefill과 decode를 몇 대 몇으로 배분할지에 따라 실제 token cost와 latency가 달라집니다.

즉 하드웨어가 동일해질수록 scheduler가 hardware utilization을 현금흐름으로 바꾸는 정도가 중요해집니다.

다만 “inference software 시장이 커진다 → 특정 독립 업체가 큰 해자를 가진다”로 바로 가면 안 됩니다. NVIDIA, hyperscaler, Kubernetes 생태계, vLLM·SGLang 같은 오픈소스가 기능을 빠르게 흡수할 수 있기 때문입니다.

더 좋은 질문은 세 가지입니다. 누가 workload telemetry를 가장 많이 가지고 있는가? 누가 router-scheduler-cache-engine을 한 피드백 루프로 묶는가? 누가 실제 고객 workload에서 latency/cost SLO를 지속적으로 최적화할 수 있는가?

여기가 장기적인 control-plane 가치가 생길 가능성이 있는 지점입니다.

13

11. 제가 이 결론을 바꿀 관측

첫째, frontier model에서 KV-cache compression과 recomputation이 크게 발전해 cache miss 비용이 매우 작아진다면 locality-aware routing의 가치는 낮아질 수 있습니다.

둘째, 초고속 rack-scale fabric이 보편화되어 KV cache를 worker 사이에 옮기는 비용이 거의 무시할 수준으로 떨어진다면 session stickiness보다 완전한 load balancing이 더 유리해질 수 있습니다.

셋째, 실제 agent production trace에서 cache-aware routing이 cache hit는 높이지만 P95/P99 latency나 GPU utilization을 개선하지 못한다면 이 구조는 과대평가된 것입니다.

반대로 여러 serving stack에서 동일 GPU 수로 cache hit↑, TTFT↓, tail latency↓, token cost↓가 반복적으로 확인된다면 AI inference의 핵심 abstraction 중 하나가

request routing → state routing

으로 이동하고 있다고 볼 수 있습니다.

오늘 5~10분 실험

간단한 시뮬레이션을 해보세요.

서버 A는 cache hit가 가능하고 queue wait가 0.5초, 서버 B는 cache miss지만 queue wait가 0.1초입니다. cache-hit 처리시간을 1초, cache-miss 처리시간을 3초라고 하면 A는 1.5초, B는 3.1초입니다.

이제 A의 queue wait를 늘려보세요. 2.1초를 넘는 순간 A의 총시간이 3.1초를 넘어 B가 더 좋아집니다.

이 2.1초가 바로 cache locality를 포기해야 하는 임계점입니다.

실제 시스템은 훨씬 복잡하지만 원리는 같습니다.
