02

핵심 질문과 결론

핵심 질문: NVMe SSD가 수백만 IOPS를 처리할 수 있는데도 애플리케이션이 그 성능을 다 쓰지 못하는 이유는 무엇일까? 단순히 더 빠른 SSD를 꽂는 것으로 충분하지 않고, 왜 Linux는 Submission Queue와 Completion Queue를 공유하는 io_uring, 그리고 NVMe 명령을 block abstraction을 덜 거쳐 전달하는 I/O Passthru 같은 경로를 만들었을까? 또 syscall을 없애거나 kernel을 우회하면 무조건 더 좋은 것일까?

결론: 현대 고성능 I/O에서는 장치 자체의 지연시간만큼 요청을 제출하고 완료를 회수하는 소프트웨어 경로의 고정비용이 중요하다. io_uring은 userspace와 kernel이 공유하는 Submission Queue(SQ)와 Completion Queue(CQ)를 중심으로 여러 요청을 batch하고, 필요하면 polling·fixed buffer·true async를 사용해 syscall, context switch, page pinning 같은 per-I/O 비용을 줄인다. FAST 2024의 I/O Passthru는 여기서 한 단계 더 나아가 IORING_OP_URING_CMD와 NVMe character interface를 이용해 새로운 NVMe 기능을 block I/O abstraction에 억지로 끼워 넣지 않고 비동기적으로 전달한다. 그러나 이것은 “abstraction을 없앨수록 좋다”는 이야기가 아니다. 더 짧은 경로는 더 높은 효율과 빠른 기능 도입을 주지만, 파일시스템·block layer가 제공하던 portability, sharing, scheduling, accounting, recovery 같은 서비스 일부를 잃거나 별도로 책임져야 한다. 핵심은 장치 성능, 소프트웨어 오버헤드, 추상화의 가치 사이에서 어느 계층에 비용을 지불할지 선택하는 것이다.

오늘의 중심 원자료는 Kanchan Joshi, Anuj Gupta, Javier González, Ankit Kumar, Krishna Kanth Reddy, Arun George, Simon Lund, Jens Axboe의 “I/O Passthru: Upstreaming a flexible and efficient I/O Path in Linux”, 22nd USENIX Conference on File and Storage Technologies(FAST ’24), 2024-02-27~29 발표 논문이다. 오늘 2026-10-02 KST에 USENIX 공식 PDF의 §2 *Motivation and Background*, §4.2 *Infusing the efficiency & scalability*, §7 *Evaluation*, §8 *Discussion*을 직접 열어 확인했다. 논문은 I/O Passthru가 mainline Linux에 들어간 NVMe I/O path이며, 핵심 구성요소로 NVMe character interface와 io_uring command를 제시한다. 03

1. 먼저 복습: 동기 I/O와 비동기 I/O의 차이는 “thread를 몇 개 쓰는가”보다 깊다

가장 단순한 동기 read()를 생각하자. 한 요청이 끝날 때까지 thread가 기다린다면 device latency 동안 CPU가 유용한 일을 못 할 수 있다. 이를 피하는 가장 쉬운 방법은 thread를 여러 개 만드는 것이다. 하지만 thread가 늘어나면 stack memory, scheduler overhead, context switching, synchronization 비용이 증가한다.

비동기 I/O의 핵심은

“요청을 제출한 execution context와 완료를 기다리는 execution context를 분리한다.”

는 것이다.

즉 한 thread가 여러 I/O를 outstanding 상태로 유지할 수 있다.

04

2. 왜 NVMe 시대에 이 문제가 더 중요해졌나

오래된 disk는 한 번의 I/O가 수 ms 걸렸다. 이때 수백 ns~수 μs의 kernel software overhead는 상대적으로 작았다. 하지만 NVMe SSD는 높은 병렬성과 매우 높은 IOPS를 제공한다. 장치가 빨라질수록 다음 비율이 커진다.

\text{software fraction}
=
\frac{t_{\text{software}}}
{t_{\text{software}}+t_{\text{device}}}.

예를 들어 교육용 가정으로

t_{\text{software}}=5\mu s,\qquad
t_{\text{device}}=5000\mu s

이면 software 비중은 약

0.1\%

뿐이다.

그런데 device latency가

50\mu s

까지 내려오면

\frac{5}{55}\approx9.1\%

가 된다.

장치가 더 빨라질수록 예전에는 무시할 수 있었던 software path가 병목으로 승격된다.

\boxed{
\text{하드웨어가 빨라질수록 주변 소프트웨어의 고정비용이 상대적으로 커진다.}
}

05

3. Queue depth: 한 요청의 latency와 전체 throughput은 다른 변수다

평균 outstanding I/O 수를 \(Q\), throughput을 \(\lambda\), 평균 I/O latency를 \(W\)라고 하자.

Little’s Law를 적용하면 정상상태에서

Q=\lambda W

이므로

\boxed{
\lambda=\frac{Q}{W}
}

이다.

[교육용 예제]

평균 latency가

W=80\mu s

라고 하자.

Queue depth가 1이면 이상화된 최대 throughput은

\lambda
=
\frac{1}{80\times10^{-6}}
=
12,500\text{ IOPS}.

Queue depth가 32이면

\lambda
=
\frac{32}{80\times10^{-6}}
=
400,000\text{ IOPS}.

장치 하나의 latency가 80μs라고 해서 throughput이 반드시 12,500 IOPS로 제한되는 것은 아니다. 여러 명령을 동시에 outstanding 상태로 두면 device 내부 병렬성을 활용할 수 있다.

그래서 modern storage API의 중요한 질문은

“한 요청을 얼마나 빨리 끝내나?”

뿐 아니라

“CPU가 충분히 싸게 많은 요청을 outstanding으로 유지할 수 있나?”

이다.

06

4. io_uring의 핵심 구조: SQ와 CQ

io_uring은 userspace와 kernel이 공유하는 두 개의 ring buffer를 중심으로 한다.

  • Submission Queue(SQ): userspace가 실행할 I/O 요청을 넣는다.
  • Completion Queue(CQ): kernel이 끝난 I/O의 결과를 넣는다.

각 submission entry를 SQE(Submission Queue Entry), completion entry를 CQE(Completion Queue Entry)라고 한다.

중심 논문은 io_uring이 userspace/kernel 경계에서 공유 SQ/CQ를 사용하고, batching, SQPoll, IOPoll, chaining을 제공한다고 설명한다. USENIX

기존 syscall 중심 모델에서는 요청마다

\text{userspace}
\rightarrow
\text{syscall}
\rightarrow
\text{kernel}
\rightarrow
\text{return}

경계를 자주 넘는다.

io_uring은 요청 descriptor 자체를 shared ring에 쌓고, 여러 요청을 한 번에 알리거나 특정 모드에서는 submission syscall을 더 줄일 수 있다.

07

5. Batching: syscall을 없애는 것보다 “고정비용을 나눠 갖는 것”

한 syscall 경계의 비용을 \(c_s\), 요청 하나를 kernel이 실제 처리하는 비용을 \(c_i\)라고 하자.

요청을 하나씩 보내면 평균 비용은

c_{\text{one}}
=
c_s+c_i.

한 syscall로 \(B\)개를 batch하면 요청당 평균 비용은

\boxed{
c_{\text{batch}}
=
\frac{c_s}{B}+c_i
}

이다.

[교육용 가정]

c_s=1.2\mu s,\qquad
c_i=0.3\mu s.

한 개씩 보내면

1.5\mu s/\text{request}.

32개를 한 번에 보내면

\frac{1.2}{32}+0.3
=
0.3375\mu s.

고정비용 \(c_s\)가 32개 요청에 분산된다.

이것이 batching의 일반적 경제학이다.

\boxed{
\text{고정비용이 크면 작업을 묶을수록 평균비용이 내려간다.}
}

하지만 batch를 모으려고 기다리면 latency가 늘 수 있다. 따라서 throughput과 tail latency 사이의 trade-off가 생긴다.

08

6. SQPOLL: syscall을 줄이지만 “공짜”는 아니다

io_uring의 SQ polling mode에서는 kernel thread가 Submission Queue를 계속 확인한다.

따라서 application이 SQE를 ring에 써두면 매번 syscall로 kernel에 알리지 않아도 처리될 수 있다.

하지만 polling thread는 CPU를 소비한다.

중심 논문의 실험에서는 512-byte random read, queue depth 128 조건에서 작은 batch size일수록 SQPOLL 효과가 컸고, batch size 2에서는 passthrough 경로의 performance가 SQPOLL 사용 시 136% 높았다고 보고한다. 동시에 저자들은 SQPOLL이 active polling을 위해 추가 CPU core를 요구한다고 명시한다. USENIX

즉

\boxed{
\text{syscall latency}
\rightarrow
\text{dedicated CPU consumption}
}

으로 비용을 바꾼 것이다.

트래픽이 적은 서비스에서 CPU core 하나를 polling에 쓰는 것은 비경제적일 수 있다. 반대로 수백만 IOPS가 필요한 storage engine에서는 합리적일 수 있다.

09

7. “Async”라고 다 같은 async가 아니다: worker-based vs true async

어떤 blocking operation을 비동기로 보이게 만드는 가장 쉬운 방법은 kernel worker thread에게 넘기는 것이다.

이것은 API 관점에서는 async처럼 보이지만 내부적으로 thread가 block된다.

중심 논문은 이를 worker-based async라고 하고, 반대로 submission path가 실제로 block하지 않도록 전체 경로를 설계하는 방식을 true async라고 부른다. 논문은 true async가 worker thread 없이 작동하는 대신, 참여하는 파일시스템·driver 등이 blocking하지 않도록 구현돼야 하므로 구현 난도가 높다고 설명한다. USENIX

논문의 Figure 3 실험에서 512-byte random read를 queue depth 증가와 함께 측정했을 때 true-async 경로는 약 3.5M IOPS까지 증가한 반면, worker-based 방식은 약 500K IOPS 수준에서 잘 늘지 않았다고 보고한다. USENIX

이 결과를 일반법칙으로 받아들이면 안 된다. 특정 workload·device·kernel 환경의 결과다.

그러나 구조적 메시지는 중요하다.

\boxed{
\text{thread로 blocking을 숨기는 것}
\neq
\text{blocking 자체를 제거하는 것}
}

이다.

10

8. Fixed buffer: 왜 memory registration이 성능기능이 되는가

I/O 장치가 userspace memory와 DMA를 하려면 kernel은 해당 user page를 찾고 고정(pin)하며 DMA mapping을 준비해야 한다.

요청마다

\text{page lookup}
\rightarrow
\text{pin}
\rightarrow
\text{DMA map}
\rightarrow
\text{I/O}
\rightarrow
\text{unmap/unpin}

을 반복하면 작은 I/O에서는 이 고정비용이 상당해진다.

io_uring의 registered/fixed buffer는 자주 재사용하는 buffer를 미리 등록해 이 작업을 amortize한다.

중심 논문도 passthrough의 uring_cmd에 fixed-buffer 기능을 연결하고, buffer를 매 I/O마다 다시 lock하지 않고 이미 등록된 region을 재사용한다고 설명한다. USENIX

이것은 database buffer pool의 page pin, RDMA memory registration, GPU pinned host memory와 같은 계열의 최적화다.

\boxed{
\text{반복 검증·매핑 비용을 upfront registration으로 이동한다.}
}

다만 pinned memory는 자유롭게 회수·이동하기 어렵기 때문에 메모리 관리 유연성을 희생한다.

11

9. 그런데 왜 또 “Passthru”가 필요한가

io_uring으로 read/write 자체는 효율화할 수 있다.

하지만 NVMe는 이제 단순 block read/write만 제공하지 않는다. 원논문은 Zoned Namespace, Key-Value, Flexible Data Placement(FDP), computational-storage 계열처럼 기존 block semantics와 다른 기능이 늘고 있다고 설명한다. USENIX

Linux 전통 경로는 대략

\text{application}
\rightarrow
\text{file API}
\rightarrow
\text{VFS/filesystem}
\rightarrow
\text{block layer}
\rightarrow
\text{NVMe driver}
\rightarrow
\text{device}

다.

이 추상화는 엄청난 장점이 있다.

애플리케이션은 SSD vendor나 NVMe command format을 몰라도 read()와 write()를 쓸 수 있다.

그런데 새로운 device-specific semantics가 block abstraction으로 표현되지 않는다면 문제가 생긴다.

논문이 던지는 질문은 이것이다.

“새 hardware feature가 생길 때마다 filesystem, block layer, syscall을 모두 고쳐야 하는가?”

12

10. 기존 passthrough의 문제: ioctl은 유연하지만 동기적이다

NVMe command를 직접 보내는 방법으로 ioctl 기반 passthrough가 있었다.

장점은 file/block abstraction을 덜 거쳐 device command에 가까운 표현을 할 수 있다는 것이다.

하지만 원논문은 기존 ioctl passthrough의 핵심 한계로 synchronous blocking interface, per-command copy/mapping overhead, block interface 의존성을 지적한다. USENIX

즉 한쪽에는

\text{generic block path}
=
\text{안정적이지만 새 semantics를 넣기 어려움}

이 있고,

다른 쪽에는

\text{ioctl passthrough}
=
\text{유연하지만 scalable async I/O에 부적합}

가 있었다.

I/O Passthru는 이 둘 사이의 새 지점을 노린다.

13

11. `IORING_OP_URING_CMD`: async ioctl에 가까운 범용 탈출구

I/O Passthru의 핵심 중 하나가 io_uring command다.

Userspace는 SQE에

\texttt{IORING\_OP\_URING\_CMD}

를 넣고 device-specific command payload를 함께 전달한다.

file descriptor가 연결된 driver는 자신의 .uring_cmd handler에서 이를 처리한다. 논문은 이 facility를 generic asynchronous-ioctl 메커니즘으로 소개한다. USENIX

즉 io_uring 자체가 NVMe command 의미를 이해할 필요는 없다.

이것은 software architecture에서 흔한 escape hatch 패턴이다.

공통 90%는 stable generic interface로 처리하고, 공통모델로 표현하기 어려운 10%는 typed extension point로 보낸다.

14

12. NVMe character interface: block device가 아닌 “NVMe generic” 입구

논문은 /dev/nvme<X>n<Y> block interface 외에 /dev/ng<X>n<Y> 형태의 NVMe generic character device를 설명한다.

이 character interface는 특정 block semantics에 종속되지 않도록 설계됐고, .uring_cmd handler를 통해 io_uring command를 받을 수 있다. USENIX

핵심은 block abstraction을 완전히 폐기하는 것이 아니다.

필요한 경우 block abstraction을 우회할 선택지를 추가한다.

15

13. 논문 실험: 209ns와 144ns가 왜 중요할까

중심 논문은 optimized kernel configuration에서 한 submission을 device까지 전달하는 kernel handler 시간을 측정했다.

  • io_uring block path의 io_read: 209 ns
  • passthrough의 io_uring_cmd: 144 ns

저자들은 passthrough handler가 약 31% 더 lean하다고 보고했다. USENIX

65ns 차이는 인간 관점에서는 아무것도 아닌 것처럼 보인다.

하지만 초당 5백만 요청이면 단순 곱으로

65ns\times5,000,000
=
0.325s

CPU-time/s에 해당한다.

즉 코어 하나의 32.5%에 해당하는 시간규모다.

이 계산은 “그 65ns가 정확히 독립적으로 CPU 32.5%를 절감한다”는 실측 주장이 아니라, nanosecond-level per-operation overhead가 수백만 IOPS에서는 거시적인 CPU 비용으로 확대될 수 있음을 보여주는 교육용 환산이다.

\boxed{
\text{작은 단위비용}\times\text{거대한 빈도}
=
\text{큰 시스템 비용}
}

이다.

16

14. 논문 결과: 더 짧은 path가 언제 실제 IOPS 차이로 나타나는가

중심 논문의 single-core 512-byte random-read 실험에서 fixed buffer와 completion polling을 함께 사용한 default kernel configuration 기준으로

\text{block path}\approx2.9M\text{ IOPS}
\text{passthrough}\approx3.9M\text{ IOPS}

를 보고했다.

performance-oriented kernel configuration에서는

3.83M
\rightarrow
5.0M\text{ IOPS}

로 passthrough가 SSD를 포화시켰다고 보고한다. USENIX

또 queue depth 1에서는 두 경로의 성능차가 거의 없었지만, queue depth가 커질수록 차이가 커져 QD16에서 passthrough가 19%, QD128에서 31% 더 많은 request를 처리했다고 보고했다. USENIX

낮은 request rate에서는 software path의 수십 ns 차이가 중요하지 않다.

높은 queue depth에서는 초당 같은 path를 수백만 번 반복하므로

\boxed{
\text{고정비용의 차이가 workload scale에 의해 증폭된다.}
}

17

15. SPDK와 비교하면 “kernel을 남겨두는 이유”가 보인다

SPDK는 대표적인 kernel-bypass storage stack이다.

User-space가 NVMe device를 직접 관리해 kernel overhead를 강하게 줄인다.

중심 논문의 두-device 실험에서 block path는 약 7.55M IOPS, passthrough와 SPDK는 약 10M IOPS를 기록했다. 하지만 두 device를 단일 CPU core에 몰아넣은 조건에서는 block 4.4M, passthrough 6M으로 SPDK보다 낮았다. USENIX

논문은 이유 중 하나로 SPDK benchmark가 NVMe device의 exclusive ownership을 갖는 반면, kernel path는 여러 사용자 사이의 sharing·synchronization과 hardware queue abstraction, tag management, timeout/abort 같은 서비스를 유지한다고 설명한다. USENIX

즉 비교대상은

\text{kernel}
\quad\text{vs}\quad
\text{no kernel}

처럼 단순하지 않다.

더 정확히는

\boxed{
\text{공유·보호·관리 서비스를 얼마나 유지하면서
fast path를 얼마나 짧게 만들 것인가}
}

의 문제다.

18

16. “추상화 세금”은 정말 세금인가

File system과 block layer를 지나면 더 많은 code가 실행된다.

성능관점에서는 abstraction tax다.

하지만 이 계층들은 device-independent API, page cache, filesystem semantics, scheduling, accounting, cgroup integration, error handling, timeout/abort, sharing과 isolation, stable userspace ABI를 제공한다.

따라서 추상화 비용은 단순 낭비가 아니다.

보험료에 더 가깝다.

좋은 질문은

“이 계층을 제거할 수 있는가?”

보다

“이 계층이 제공하는 어떤 서비스를 이 workload는 실제로 필요로 하는가?”

다.

19

17. 2026년의 확장: io_uring은 storage API를 넘어 “kernel/userspace async transport”가 된다

오늘 2026-10-02에 확인한 최신 Linux kernel documentation의 io_uring zero copy Rx는 network receive path에서 kernel-to-userspace payload copy를 없애고 packet payload를 userspace memory로 직접 받게 한다. 다만 packet header는 kernel TCP stack에서 정상 처리된다. 또한 header/data split, flow steering, RSS 같은 NIC 기능이 필요하다. 리눅스 커널 아카이브

Linux kernel — io_uring zero copy Rx

또 최신 FUSE-over-io-uring 문서는 userspace filesystem daemon과 kernel의 통신에 IORING_OP_URING_CMD를 사용하고, per-CPU queue, registered buffer pool, zero-copy 경로를 설명한다. 문서 자체는 현재 interface가 아직 개발 중이며 바뀔 수 있다고 명시한다. 리눅스 커널 아카이브

Linux kernel — FUSE-over-io-uring design documentation

이 두 사례는 io_uring이 단순히

“빠른 read/write syscall”

에서

“kernel과 userspace가 고성능 비동기 요청·완료를 교환하는 공통 transport”

로 역할이 넓어지고 있음을 보여준다.

20

18. 2026년 DBMS 연구가 주는 반론: API를 바꾸는 것만으로는 안 된다

2026년 PVLDB의 “High-Performance DBMSs with io_uring: When and How to Use It”는 io_uring을 DBMS에 넣을 때 단순 drop-in replacement만으로 performance benefit이 보장되지 않는다고 강조한다.

저자들은 storage-bound buffer manager와 network-bound analytical shuffle을 분석하고, registered buffers와 passthrough 같은 기능을 평가한다. 또한 PostgreSQL의 io_uring integration에 자신들의 guideline을 적용한 case study에서 14% performance improvement를 보고한다. DFKI

High-Performance DBMSs with io_uring — DFKI/PVLDB 2026

이 결과가 중요한 이유는 다음이다.

\boxed{
\text{좋은 primitive}
\neq
\text{좋은 system architecture}
}

이다.

Application이 충분한 concurrency를 노출하지 못하거나, batching이 작거나, buffer lifecycle이 맞지 않거나, workload 자체가 CPU-bound라면 io_uring의 낮은 overhead는 end-to-end 성능으로 이어지지 않는다.

21

19. 시스템 렌즈: 병목은 제거되는 것이 아니라 이동한다

처음에는 device latency가 병목이다.

SSD가 빨라지면 kernel path가 병목이 된다.

io_uring으로 syscall 비용을 줄이면 page pinning과 DMA mapping이 보인다.

fixed buffer로 이를 줄이면 completion processing이나 polling CPU가 보인다.

passthrough로 path를 줄이면 device 자체가 다시 포화된다.

\boxed{
\text{병목을 제거하면 시스템이 빨라지는 동시에
다음 병목이 더 잘 보인다.}
}

Roofline 모델에서 compute bottleneck을 없애면 memory bottleneck이 나타났던 것과 같은 구조다.

22

20. 경제학 렌즈: Polling은 idle capacity를 latency와 교환한다

Interrupt 기반 system은 일이 없으면 CPU를 쉬게 할 수 있다.

Polling은 CPU가 계속 확인한다.

즉 polling은

\text{CPU idle capacity}

를 소비해서

\text{wake-up latency와 interrupt overhead}

를 줄인다.

전력·CPU core가 비싼 환경에서는 polling의 기회비용이 크다.

반대로 storage appliance처럼 latency와 throughput이 핵심이고 CPU core를 전용할 수 있다면 polling의 기대가치가 높다.

따라서

\boxed{
\text{polling vs interrupt}
}

는 기술선택이면서 자원가격 선택이다.

23

21. 조직·아키텍처 렌즈: Stable core와 fast-moving edge

Linux kernel은 userspace ABI를 오랫동안 유지해야 한다.

반면 NVMe hardware interface는 빠르게 변한다.

모든 새로운 hardware feature를 filesystem과 block layer에 즉시 넣으면 stable core가 빠르게 복잡해진다.

반대로 아무것도 넣지 않으면 innovation이 kernel을 우회하게 된다.

I/O Passthru의 설계는 조직설계로 보면

\boxed{
\text{stable core}
+
\text{controlled extension point}
}

패턴이다.

중앙 정책은 안정적으로 유지하고, 변화가 빠른 영역에는 승인된 extension interface를 제공하는 것과 같다.

24

22. 인센티브 렌즈: benchmark 숫자 하나를 최적화하면 무엇을 잃을까

IOPS만 KPI라면 가장 쉬운 길은 많은 보호·공유 기능을 끄고 hardware를 단독 점유하는 것이다.

하지만 production system의 목적함수는 더 복잡하다.

U
=
f(
\text{throughput},
\text{p99 latency},
\text{CPU},
\text{energy},
\text{isolation},
\text{recovery},
\text{operability}
).

Benchmark가 IOPS 하나만 측정한다면 개발팀은 IOPS에 보이지 않는 기능을 제거할 인센티브를 가진다.

그래서 성능비교에서 “누가 더 빠른가?”보다 먼저

“각 경로가 어떤 서비스를 제공하는 상태에서 비교했는가?”

를 확인해야 한다.

25

23. 실무에서 어떤 API를 골라야 하나

보통의 file server, 일반 application, low-to-medium IOPS workload라면 전통적인 file API와 mature filesystem이 주는 단순성·안전성의 가치가 더 클 수 있다.

고성능 database/storage engine처럼 많은 outstanding I/O, direct I/O, explicit buffer management가 있고 CPU overhead가 실제 병목이라면 io_uring의 batching, fixed buffer, true async의 가치가 커진다.

새 NVMe command semantics를 직접 활용해야 하고 block abstraction이 병목이나 표현 제약이라면 I/O Passthru가 후보가 된다.

극단적으로 device를 독점할 수 있고 kernel service보다 absolute performance와 control이 중요하면 SPDK 같은 kernel-bypass 접근도 선택지가 된다.

\boxed{
\text{가장 낮은 계층의 API}
\neq
\text{항상 가장 좋은 API}
}

이다.

좋은 선택은 필요한 abstraction service와 workload 병목의 교집합에서 나온다.

26

오늘 기억할 한 문장

\boxed{
\text{io_uring의 핵심은 “syscall을 없애는 것”이 아니라
많은 I/O를 싸게 outstanding 상태로 유지하고 완료를 효율적으로 회수하는 것이다.}
}

그리고 I/O Passthru의 더 넓은 교훈은 이것이다.

\boxed{
\text{좋은 시스템은 추상화를 무조건 제거하지 않는다.
비싼 fast path에서 불필요한 추상화만 우회하면서,
필요한 보호·관리 기능은 남긴다.}
}

SSD가 빨라질수록 성능문제는 hardware specification에서 software architecture 문제로 이동한다.

PAUSE & REFLECT

잠깐, 내 언어로 설명해 보기

Q1.

평균 device+software latency가

W=100\mu s

라고 하자.

1. Queue depth \(Q=1\)일 때 Little’s Law로 이상화된 throughput을 구하라.
2. \(Q=64\)이면 얼마인가?
3. 실제 throughput이 이 숫자보다 낮을 수 있는 이유를 세 가지 설명하라.

해설 보기 +

Little’s Law에서

Q=\lambda W

이므로

\lambda=\frac{Q}{W}.

\(Q=1\)이면

\lambda
=
\frac{1}{100\times10^{-6}}
=
10,000\text{ IOPS}.

\(Q=64\)이면

\lambda
=
\frac{64}{100\times10^{-6}}
=
640,000\text{ IOPS}.

실제값은 device 내부 최대 IOPS, software submission bottleneck, contention, queue saturation, tail latency, CPU 한계 등 때문에 더 낮을 수 있다.

Q2.

요청마다 syscall fixed cost가

c_s=800ns

이고 kernel 내부 per-request cost가

c_i=250ns

라고 하자.

1. 요청을 한 개씩 제출할 때 요청당 비용을 구하라.
2. batch size 16이면 요청당 평균 제출비용을 구하라.
3. batch size를 무한히 키우면 요청당 비용의 하한은 무엇인가?
4. batch size가 너무 크면 latency가 왜 나빠질 수 있는가?

해설 보기 +

한 개씩이면

800+250
=
1050ns.

Batch size 16이면

\frac{800}{16}+250
=
50+250
=
300ns.

Batch가 매우 커지면

\frac{c_s}{B}\to0

이므로 하한은

\boxed{250ns}

다.

하지만 요청을 충분히 모으기 위해 기다려야 하므로 batch-formation delay가 생길 수 있다. Throughput 최적 batch와 latency 최적 batch는 다를 수 있다.

Q3.

다음 두 storage path가 있다.

A:

  • 3.8M IOPS
  • kernel filesystem/block services 사용
  • CPU 1 core

B:

  • 5.0M IOPS
  • polling thread 1개 추가
  • fixed registered memory 8GB 필요
  • 일부 filesystem/block abstraction 우회

1. IOPS만 보면 B가 몇 % 높은가?
2. 이것만으로 B가 “더 좋은 설계”라고 결론낼 수 없는 이유를 설명하라.
3. 어떤 workload와 운영조건이라면 B의 선택이 정당화될 가능성이 높은가?

해설 보기 +

IOPS 증가율은

\frac{5.0-3.8}{3.8}
\approx31.6\%.

하지만 B는 CPU core 한 개를 polling에 더 사용하고 8GB pinned memory와 더 복잡한 운영·복구 책임을 요구한다.

따라서 전체 효용은 IOPS만이 아니라

\text{IOPS/core},
\quad
\text{IOPS/watt},
\quad
\text{p99 latency},
\quad
\text{memory cost},
\quad
\text{reliability}

를 포함해 비교해야 한다.

B는 수백만 IOPS가 실제 business bottleneck이고 CPU·memory를 전용할 수 있으며, device semantics를 직접 활용할 가치가 큰 database/storage appliance에 더 적합할 수 있다.
