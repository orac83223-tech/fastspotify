02

오늘의 질문: AI 에이전트가 돈·데이터를 바꾸기 시작하면 왜 ACID가 다시 중요해질까?

오늘 비교한 세 후보는 ① AI 에이전트가 실제 업무를 수행할수록 왜 데이터베이스의 ACID 개념이 다시 중요해지는가, ② 재시도(retry)가 왜 신뢰성을 높이면서 동시에 중복 결제·중복 승인 같은 사고를 만들 수 있는가, ③ 장시간 에이전트에서 “모델이 똑똑한가”보다 “중간 상태와 외부 효과를 얼마나 정확히 관리하는가”가 더 중요한가였습니다. 최근에는 온톨로지, AI 코드 검증, 장기기억, KV cache처럼 ‘AI 주변의 시스템’이 성능을 좌우하는 주제를 연속해서 봤습니다. 오늘은 그 흐름을 한 단계 더 밀어, AI가 읽고 답하는 수준을 넘어 실제 시스템을 변경할 때 필요한 트랜잭션 사고를 보겠습니다.

핵심 통찰은 이렇습니다. AI 에이전트의 가장 위험한 실패는 틀린 문장을 생성하는 것이 아니라, 일부는 이미 실행됐는데 에이전트가 그 사실을 잊고 같은 행동을 다시 수행하는 것입니다. 이메일을 두 번 보내고, 환불을 두 번 실행하고, 배치를 중복 기동하고, 승인 전에 운영 반영을 해버리는 문제입니다. 이 순간부터 핵심 질문은 “모델 정확도가 몇 %인가?”가 아니라 “한 작업이 중간에 죽어도 외부 세계를 일관된 상태로 남길 수 있는가?”가 됩니다.

03

1. 에이전트는 챗봇이 아니라 ‘긴 트랜잭션’이 되어가고 있다

전통적인 챗봇은 비교적 단순했습니다.

질문 → 모델 호출 → 답변

한 번 실패하면 사용자가 다시 질문하면 됩니다. 실패 비용도 대체로 낮습니다.

하지만 에이전트는 요구사항 해석 → DB 조회 → 문서 검색 → 코드 작성 → 테스트 → 승인 요청 → API 호출 → 운영 반영 → 이메일 발송처럼 움직입니다. 이 과정이 30분, 몇 시간, 며칠에 걸쳐 이어질 수도 있습니다. Microsoft의 2026년 Durable Task 문서는 실제 에이전트가 수 시간·수일·수주 동안 상태를 유지하며 외부 도구와 사람 승인을 기다릴 수 있다고 설명하고, 체크포인트·재시도·상태 복구를 별도 인프라 문제로 다룹니다. (Microsoft Learn) Microsoft — AI 에이전트를 위한 Durable Task

여기서 중요한 변화가 생깁니다. 모델 호출 하나는 짧지만 업무 전체는 장시간 상태를 가진 분산 시스템이 됩니다.

즉 에이전트의 신뢰성 문제는 LLM 문제만이 아니라 데이터베이스, 메시징, 워크플로 엔진, API 설계, 내부통제 문제가 됩니다.

04

2. 가장 위험한 순간은 ‘외부 효과는 성공했는데 성공 기록은 남지 않은 순간’이다

예를 들어 에이전트가 고객에게 10만원을 환불한다고 합시다.

에이전트가 환불 API를 호출했고 결제 시스템에서는 환불이 성공했는데 성공 응답이 네트워크에서 유실될 수 있습니다. 에이전트는 실패했다고 판단하고 retry하고, 환불이 또 실행될 수 있습니다.

이것은 AI 특유의 문제가 아닙니다. 분산시스템에서 아주 오래된 문제입니다.

문제는 에이전트가 등장하면서 이런 side effect의 수가 급증한다는 것입니다. 사람은 보통 “환불” 버튼을 한 번 누르지만 에이전트는 네트워크 오류, timeout, model retry, tool retry, workflow restart 때문에 같은 행동을 여러 번 시도할 수 있습니다.

AWS의 2026 Agentic AI Lens는 그래서 에이전트 작업에 deterministic idempotency key를 사용하고, 동일 logical operation의 retry가 같은 key를 사용하도록 권고합니다. 이미 성공한 작업이면 외부 효과를 다시 실행하지 않고 기존 결과를 반환하는 방식입니다. (AWS Documentation) AWS — Implement idempotent task execution patterns

05

3. Idempotency는 ‘두 번 호출해도 한 번 실행된 것처럼 보이게 하는 능력’이다

수학에서 함수 \(f\)가

f(f(x))=f(x)

를 만족하면 idempotent하다고 합니다.

시스템에서는 의미가 조금 실용적으로 바뀝니다.

“같은 논리적 작업을 여러 번 요청해도 외부 결과는 한 번 실행한 것과 같아야 한다.”

Stripe는 POST 요청에 idempotency key를 제공하고, 같은 key로 재요청하면 첫 요청의 결과를 재사용하도록 설계합니다. 연결 오류 때문에 클라이언트가 retry해도 같은 결제를 두 번 만들지 않게 하기 위해서입니다. (Stripe Docs) Stripe — Idempotent requests

에이전트 시스템에서는 이 원칙이 훨씬 중요해집니다.

예를 들어 workflow_id = CHANGE-20261002-017, step = SEND_APPROVAL, recipient = user@example.com이라면 idempotency key를 개념적으로

hash(workflow\_id+step+recipient)

처럼 만들 수 있습니다.

실제 구현은 더 많은 버전 정보와 입력 hash가 필요할 수 있지만 핵심은 같습니다. 같은 업무의 같은 단계가 retry되면 같은 key가 생성돼야 합니다.

06

4. ‘retry를 많이 하면 안정적’이라는 직관은 절반만 맞다

분산시스템에서는 일시적 실패를 극복하기 위해 retry를 많이 씁니다.

성공확률이 매 시도마다 \(p\)이고 독립이라는 아주 단순한 가정을 두면 \(n\)번 안에 한 번 이상 성공할 확률은

P(success)=1-(1-p)^n

입니다.

한 번 성공확률이 0.8이라면 세 번까지 retry할 때

1-0.2^3=99.2\%

가 됩니다.

그래서 retry는 강력합니다.

하지만 side effect가 있는 작업에서는 문제가 반대 방향으로 생깁니다.

성공 여부를 모르는데 재시도하면 성공확률뿐 아니라 중복 실행확률도 올라갑니다.

따라서

retry without idempotency = 사고를 증폭할 수 있는 복구 메커니즘

입니다.

이 점은 품질관리에서도 중요합니다. “오류 시 3회 재시도”라는 설계는 장애대응처럼 보이지만, 결제·메일·배치기동·권한부여·DB 변경에서는 반드시 “재시도가 안전한가?”를 같이 검토해야 합니다.

07

5. ACID를 에이전트에 적용하면 의미가 조금 달라진다

2026년 8월 14일 공개된 「Agentic Transaction: Towards ACID-Compliant Agent Systems」는 데이터베이스의 ACID 개념을 장기 실행 에이전트로 확장하려고 시도합니다.

전통적인 ACID는 Atomicity — 전부 성공하거나 전부 실패한다, Consistency — 유효한 상태에서 유효한 상태로 이동한다, Isolation — 동시에 실행되는 작업들이 서로 중간 상태를 망가뜨리지 않는다, Durability — commit된 결과는 장애가 나도 남는다는 네 가지입니다.

이 논문은 이를 Semantic Atomicity, Semantic Consistency, Semantic Isolation, Semantic Durability로 재해석합니다. 저자들은 제안한 ACID-Agent가 실험한 benchmark에서 Claude Code를 포함한 비교 agent보다 최대 10.6% 높은 overall score를 보였다고 보고합니다. 아직 2026년 8월 arXiv preprint이며 특정 데이터 에이전트 benchmark 결과이므로 일반적인 프로덕션 성능으로 확대해석해서는 안 됩니다. (arXiv) Agentic Transaction 원문

이 논문의 더 중요한 부분은 숫자가 아니라 질문 자체입니다.

“LLM이 만든 행동을 곧바로 현실에 commit해도 되는가?”

데이터베이스는 수십 년 동안 이 문제에 대해 “아니다. 검증하고, 격리하고, commit point를 만들어야 한다”고 답해왔습니다.

08

6. Atomicity가 어려운 이유: 현실 세계에는 ROLLBACK이 없는 행동이 많다

DB 내부에서는 transaction이 실패하면 ROLLBACK할 수 있습니다.

하지만 현실의 에이전트는 이메일 발송, 주문 제출, 고객 문자 발송, 외부기관 API 호출, 운영 배치 실행, 파일 삭제, 결제 승인 같은 일을 할 수 있습니다.

이 중 일부는 정확히 되돌릴 수 없습니다.

이메일을 보낸 뒤 ROLLBACK EMAIL을 실행한다고 상대의 받은편지함에서 메시지가 사라지지 않습니다.

그래서 분산시스템은 장기 transaction에 Saga 패턴을 사용합니다. 각 작업을 하나의 거대한 DB transaction으로 잠그는 대신 단계별로 commit하고, 뒤 단계가 실패하면 앞 단계의 영향을 되돌리는 compensating transaction을 실행합니다. AWS Prescriptive Guidance도 Saga를 여러 서비스 사이의 장기 transaction을 위한 실패관리 패턴으로 설명합니다. (AWS Documentation) AWS — Saga pattern

예를 들어

예약 생성 → 결제 → 쿠폰 사용

에서 마지막 쿠폰 단계가 실패하면 전체 DB를 시간여행시키는 것이 아니라

결제 취소 → 예약 취소

라는 보상 동작을 수행합니다.

AI 에이전트도 같은 사고가 필요합니다.

09

7. 그래서 좋은 에이전트 tool은 execute() 하나만 있으면 부족하다

에이전트에게 아래 함수 하나만 준다고 생각해보세요.

deploy_to_production()

이 함수가 성공 중인지 실패했는지 애매한 상태에서 agent process가 죽으면 복구가 매우 어렵습니다.

조금 더 나은 tool contract는 개념적으로 prepare(), validate(), execute(idempotency_key), status(operation_id), compensate(operation_id), audit_log(operation_id) 같은 정보를 갖습니다.

즉 tool 자체가 transaction semantics를 노출해야 합니다.

이것은 AI 모델의 지능과 별개입니다.

모델이 훨씬 더 똑똑해져도 API가 “요청을 받았는지 모르겠고 다시 부르면 두 번 실행될 수 있습니다”라면 안전한 자동화가 어렵습니다.

그래서 agent 시대에는 좋은 API가 좋은 프롬프트만큼 중요해질 수 있습니다.

10

8. Consistency는 DB constraint에서 ‘업무 불변식’으로 확장된다

데이터베이스에서는 consistency를 PK, FK, CHECK constraint 같은 규칙과 연결해서 생각하기 쉽습니다.

에이전트에서는 더 상위의 업무 불변식이 필요합니다.

예를 들어 프로그램 변경통제를 생각하면 운영 반영된 변경에는 승인 기록이 있어야 하고, 고위험 변경에는 테스트 결과가 있어야 하며, 긴급변경은 사후승인 deadline을 가져야 하고, 배치 실행은 승인된 작업시간과 일치해야 한다는 식입니다.

이런 규칙은 SQL schema만으로 모두 표현하기 어렵습니다.

그래서 AI agent의 consistency layer는

DB constraint + business rule + policy engine + workflow state machine + human approval

을 함께 사용하게 됩니다.

앞서 온톨로지를 다뤘을 때 Entity + Relation + State + Action + Policy가 중요하다고 봤다면, 오늘의 transaction 관점은 여기에 Commit + Rollback/Compensation + Audit를 추가합니다.

11

9. Isolation은 더 이상 DB row lock만의 문제가 아니다

두 에이전트가 동시에 같은 고객이나 같은 프로그램 변경건을 처리하면 어떤 일이 생길까요?

Agent A는 오전 10시에 정책 문서 v1을 읽습니다. 그 사이 관리자가 정책을 v2로 변경합니다. Agent B는 v2를 읽습니다. Agent A는 오래된 v1에 근거해 오후 2시에 실행합니다.

DB 자체에서는 아무 충돌이 없을 수 있습니다.

하지만 Agent A의 reasoning은 이미 stale해졌습니다.

2026년 8월 공개된 「BEGIN AI TRANSACTION: Semantic Isolation for Durable AI Workflows」는 이 문제를 semantic read skew, compatibility skew 같은 형태로 정의합니다. 저자들은 공개 LangGraph 코드베이스 표본을 조사해 durable workflow 안에서 live semantic resource를 다시 resolve하는 패턴을 보고했고, version binding과 semantic snapshot 같은 격리 개념을 제안했습니다. 이 역시 preprint이므로 연구 방향으로 보는 것이 적절합니다. BEGIN AI TRANSACTION 원문

이것은 소프트웨어 형상관리와 아주 비슷합니다.

코드를 테스트할 때 v1 소스로 테스트했는데 배포 직전에 dependency가 v2로 바뀌면 테스트 증거가 약해집니다.

AI agent도 reasoning에 사용한 prompt, policy, model, retrieval index, tool schema의 version을 기록해야 할 수 있습니다.

12

10. ‘결정적 workflow + 비결정적 LLM’ 조합이 실용적인 이유

LLM은 본질적으로 비결정적일 수 있습니다.

같은 질문에도 다른 계획을 만들 수 있습니다.

그렇다고 전체 시스템까지 비결정적일 필요는 없습니다.

Microsoft Durable Task는 workflow를 크게 두 방식으로 구분합니다. 첫째, deterministic workflow 안에서 LLM을 하나의 step으로 사용합니다. 둘째, LLM이 다음 tool과 순서를 결정하는 agent loop를 사용합니다. 두 경우 모두 checkpoint와 durable state를 적용할 수 있습니다. (Microsoft Learn) Microsoft — Agent application patterns

이 구조가 중요한 이유는 생각은 유연하게, commit은 엄격하게 만들 수 있기 때문입니다.

LLM이 “나는 A → C → B 순서로 하는 것이 좋겠습니다”라고 제안해도 runtime은 “좋다. 하지만 C 실행 전에는 정책검증과 승인 token이 필요하다”고 제한할 수 있습니다.

이 역할분리가 장기적으로 가장 현실적인 agent control architecture 중 하나일 수 있습니다.

13

11. 장기 에이전트의 진짜 자산은 ‘생각의 연속성’보다 ‘효과의 원장’일 수 있다

사람들은 agent memory를 대화기억 중심으로 생각하기 쉽습니다.

하지만 실제 운영에서는 무엇을 이미 실행했는가, 그 실행은 성공했는가, 누가 승인했는가, 어떤 입력과 정책 version을 사용했는가, 실패하면 어떤 보상작업이 필요한가가 더 중요합니다.

즉 agent memory에는 두 종류가 있습니다.

Epistemic memory — 무엇을 알고 있는가.

Operational ledger — 무엇을 했는가.

둘을 섞으면 위험합니다.

“내 기억으로는 이메일을 안 보낸 것 같다”와 “메일 서버가 operation_id=123을 SENT로 기록했다”는 증거 수준이 다릅니다.

금융에서 사람의 기억보다 원장을 믿는 이유와 같습니다.

AI agent에서도 중요한 행동은 LLM memory가 아니라 append-only event log와 external system receipt를 source of truth로 삼는 편이 안전합니다.

14

12. 비용 관점에서도 durable execution은 보험이 아니라 재작업 방지 장치다

100단계 agent가 있다고 합시다.

각 단계 비용을 단순히 1이라고 두고 92번째 단계에서 실패했다고 하면 처음부터 다시 시작할 경우 91의 이미 지불한 비용을 다시 냅니다.

checkpoint가 있다면 마지막 성공지점부터 재개할 수 있습니다.

Temporal은 2026년 글에서 100단계 workflow의 92번째 prompt를 100개 variant로 실험하는 예를 들며, 앞 91단계를 replay하고 뒷부분만 다시 실행하면 전체 재실행 대비 실행 step 수를 크게 줄일 수 있다고 설명합니다. 공급업체의 예시 계산이므로 일반적인 절감률로 받아들일 필요는 없지만, workflow가 길수록 이미 완료한 계산을 보존하는 경제적 가치가 커진다는 원리는 타당합니다. (Temporal) Temporal — Building AI agents that overcome the complexity cliff

이것은 투자에서 sunk cost와는 다릅니다.

이미 끝난 잘못된 프로젝트를 계속하는 것은 매몰비용 오류입니다.

반면 검증된 중간 산출물을 재사용하는 것은 재작업 방지입니다.

과거 비용을 이유로 미래의 나쁜 결정을 유지하는 것과, 과거에 이미 산출한 유효한 계산을 다시 쓰는 것은 구분해야 합니다.

15

13. 내부통제 관점에서는 ‘누가 승인했나’보다 ‘무엇에 승인했나’가 더 중요해진다

AI agent가 변경요청 초안을 만들고 사람이 승인하고 그 후 agent가 실제 운영 반영을 한다고 합시다.

겉으로는 human-in-the-loop입니다.

하지만 승인 이후 agent가 대상 파일이나 SQL을 바꾸면 어떻게 될까요?

사람은 A를 승인했는데 시스템은 B를 실행합니다.

그래서 중요한 통제는 단순 approval flag가 아닙니다.

승인 대상 artifact의 hash와 실제 실행 artifact의 hash가 같아야 합니다.

즉 승인자, 승인시간, 승인한 계획 version, 승인한 코드/hash, 실제 실행된 코드/hash를 연결해야 합니다.

이는 전통적인 프로그램 변경통제의 “승인받은 소스와 운영 반영 소스의 동일성” 문제와 정확히 같습니다.

AI agent가 들어오면 이 통제의 중요성이 줄어드는 것이 아니라 더 커집니다. Agent는 승인 후에도 코드를 다시 생성할 수 있기 때문입니다.

16

14. 가장 강한 반론: ACID를 너무 강하게 적용하면 agent의 장점이 사라지지 않을까?

맞는 반론입니다.

모든 agent 행동을 global serializable transaction처럼 만들면 너무 느리고 복잡해질 수 있습니다.

읽기 전용 검색, 초안 작성, 로그 분석처럼 side effect가 없는 행동에는 강한 transaction이 필요하지 않습니다.

반대로 송금, 권한 변경, 운영배포, 고객 통지처럼 되돌리기 어려운 작업은 강한 통제가 필요합니다.

따라서 가장 현실적인 설계는 risk-tiering입니다.

낮은 위험은 자유롭게 탐색하고 실패해도 다시 실행합니다. 중간 위험은 checkpoint + idempotency + validation을 적용합니다. 높은 위험은 immutable plan + approval + policy check + idempotency + commit record + compensation + audit까지 붙입니다.

즉 모든 곳에 같은 통제를 적용하는 것이 아니라 행동의 비가역성과 손실 규모에 비례해 transaction 강도를 높이는 것이 합리적입니다.

이것은 금융의 한도관리, 보안의 least privilege, 품질관리의 위험기반 테스트와 같은 원리입니다.

17

15. 투자·전략 렌즈: 에이전트 시대의 해자는 ‘더 똑똑한 모델’뿐 아니라 ‘commit layer’에도 생길 수 있다

모델 성능이 비슷해질수록 기업이 agent에게 실제 업무를 맡길 때 차이는 다른 곳에서 생길 수 있습니다.

누가 긴 workflow를 복구할 수 있는가. 누가 duplicate action을 막는가. 누가 approval과 실제 execution을 구조적으로 묶는가. 누가 모든 effect에 audit trail을 남기는가. 누가 과거 workflow version을 재현할 수 있는가.

이것들은 데이터베이스, workflow engine, identity, policy, observability, event log가 만나는 영역입니다.

경제학적으로 보면 모델은 ‘의사결정 생산비’를 낮추고, 그 결과 실행 횟수를 폭증시킬 수 있습니다.

실행이 많아질수록 아주 작은 오류율도 절대 사고건수로 확대됩니다.

하루 100건 × 사고확률 0.1%라면 기대 사고는 0.1건입니다. 하루 100,000건 × 사고확률 0.1%라면 기대 사고는 100건입니다.

따라서 자동화 규모가 커질수록 reliability investment의 기대값도 커집니다.

AI가 싸질수록 통제가 덜 필요해지는 것이 아니라, AI가 너무 많이 행동하기 때문에 단위 행동당 통제비용을 자동화해야 하는 방향으로 갈 가능성이 큽니다.

18

제가 이 결론을 바꿀 관측

향후 실제 production agent가 수백~수천 단계의 tool call과 외부 변경을 수행하면서도 별도의 durable workflow, idempotency, version binding, compensation 없이 장기간 매우 낮은 사고율을 유지한다면 transaction layer의 중요성을 지금보다 낮춰야 합니다.

또 external API 대부분이 자연스럽게 exactly-once semantics를 제공하고, agent runtime이 모든 effect를 자동 감지·복구할 수 있게 된다면 개발자가 직접 설계할 영역도 줄어들 수 있습니다.

반대로 agent 사용량이 늘면서 사고의 주요 원인이 “모델이 잘못 추론함”보다 “retry 중복 실행, 오래된 state, 잘못된 version, 부분실행, 승인과 실행의 불일치”에서 반복적으로 나온다면, 앞으로 enterprise agent의 핵심 경쟁력은 model benchmark보다 transaction correctness에 가까워질 것입니다.

오늘 5~10분 실험

평소 반복되는 업무 하나를 고르세요.

예를 들어

테스트 결과 확인 → 승인 요청 → 운영 반영 → 완료메일

이라고 합시다.

각 단계에서 네 가지만 확인합니다.

R — retry해도 안전한가?
I — idempotency key가 있는가?
C — 실패하면 compensate할 수 있는가?
A — 실행 증거(audit)가 남는가?

예를 들어 이메일 발송 단계가 R: 위험 / I: 없음 / C: 사실상 불가 / A: 메일 서버 Sent 로그 있음이라면 이 단계는 agent에게 단순 함수처럼 넘기기 위험합니다.

이메일 전송 전에 deterministic operation_id를 만들고, 전송 후 message_id를 저장하고, retry 전에 기존 message_id를 조회하는 식으로 tool contract를 바꿔야 합니다.

이 작은 연습을 해보면 AI agent 품질은 prompt의 품질만이 아니라 tool의 transaction semantics에서 결정된다는 점이 보입니다.
