eBPF 검증기의 역설: 커널을 지키는 정적 분석기는 누가 검증하는가?

사용자가 작성한 프로그램을 운영체제 커널 내부에서 빠르게 실행하려면 위험하다. eBPF는 실행 전에 검증기(verifier)를 통과시키는 방식으로 이 문제를 해결한다. 그런데 검증기는 모든 입력값을 직접 실행하지 않고도 메모리 접근이 안전하다고 어떻게 판단할까?

02

핵심 질문과 결론

핵심 질문: 사용자가 작성한 프로그램을 운영체제 커널 내부에서 빠르게 실행하려면 위험하다. eBPF는 실행 전에 검증기(verifier)를 통과시키는 방식으로 이 문제를 해결한다. 그런데 검증기는 모든 입력값을 직접 실행하지 않고도 메모리 접근이 안전하다고 어떻게 판단할까? 더 근본적으로, 그 검증기가 잘못 판단하면 누구에게 들킬까?

결론: eBPF 검증기는 실제 실행상태를 더 넓은 *추상상태(abstract state)*로 감싸는 추상해석(abstract interpretation)을 수행한다. 안전성을 증명하려면 실제로 도달 가능한 모든 상태가 추상상태 안에 있어야 한다.

2024년 OSDI 논문은 이 원칙을 거꾸로 활용했다. 실제 실행에서 관측한 상태를 프로그램 안에 다시 심어 놓고, 검증기 자신이 그 상태를 가능하다고 보는지 시험하는 state embedding이다.

연구진은 당시 실험에서 한 달 동안 이전에 알려지지 않은 검증기 논리오류 15개를 발견했으며, 논문 제출 당시 10개가 수정됐다고 보고했다. 이 숫자는 2024년 실험 결과이지 현재 미수정 취약점 수가 아니다. USENIX

1. eBPF가 왜 커널 안에서 실행되는가

운영체제의 일반 애플리케이션은 보통 사용자 공간(user space)에서 동작하고, 파일·네트워크·프로세스 관리처럼 권한이 필요한 일은 커널에 요청한다.

그러나 모든 패킷이나 시스템 이벤트를 사용자 공간으로 옮겨 분석하면 전환 및 데이터 이동 비용이 발생한다.

eBPF는 제한된 프로그램을 커널 안의 여러 hook에 연결해 네트워크 처리, 성능 관측, 정책 집행 등을 수행한다. 적절한 조건에서 JIT 컴파일을 통해 native instruction으로 실행할 수도 있다.

문제는 커널 공간의 오류가 단일 애플리케이션 장애로 끝나지 않을 수 있다는 점이다.

범위를 벗어난 메모리 접근, 초기화되지 않은 값 사용, 잘못된 포인터, 종료가 보장되지 않는 제어흐름이 위험하다. 그래서 eBPF 프로그램은 적재 전에 검증을 거친다.

실제 적재 가능 여부는 커널 버전, 프로그램 종류, 권한, helper/kfunc 계약에 따라 달라진다.

검증기를 통과했다는 말은 임의의 기능적 정답을 보증한다는 뜻이 아니라, 검증기가 맡은 안전조건을 만족한다고 판정했다는 뜻이다. Kernel.org

2. 선수개념: 구체상태와 추상상태

8비트 부호 없는 레지스터 r의 실제 값은 0부터 255까지 하나다. 하지만 프로그램을 실행하기 전에는 그 값을 모른다.

정적 분석기는 값 하나 대신 가능한 값의 집합을 다룬다.

구체상태 집합을 \(S\), 추상상태를 \(A\)라고 하고, 추상상태의 뜻을 구체값 집합으로 바꾸는 함수를 \(\gamma\)(감마)라고 하자.

예를 들어 구간 추상도메인에서는

A=[0,255]
\gamma(A)=\{0,1,\ldots,255\}

다.

이제 r에 비트 연산

r &= 15;

를 실행하면 실제 결과는 반드시 0~15에 든다.

따라서 추상분석기는 결과를

[0,15]

로 좁혀도 안전하다.

중요한 것은 추상의 정확도가 아니라 과소추정하지 않는 성질이다.

결과를

[0,7]

이라고 잘못 판단하면 실제로 가능한 12가 빠진다.

검증기가 “12인 경우는 발생하지 않는다”고 판단하고 위험한 분기를 무시할 수 있다.

이를 수식으로 쓰자.

실제 명령의 상태변환을 \(F\), 추상상태의 변환을 \(F^\#\)라 하면 건전성(soundness)의 핵심 조건은

\boxed{
\{F(s)\mid s\in\gamma(A)\}
\subseteq
\gamma(F^\#(A))
}

이다.

좌변은 실제로 가능한 다음 상태, 우변은 분석기가 허용한 다음 상태다.

실제 상태가 추상상태 바깥으로 빠져나가서는 안 된다.

3. 왜 안전을 위해 일부 정상 프로그램까지 거절할까

추상분석은 일반적으로 정확한 값 대신 안전한 범위를 사용한다.

따라서 실제로는 절대 발생하지 않는 조합도 가능한 것으로 간주할 수 있다.

이런 과대근사(over-approximation)는 거짓 경보(false positive), 즉 안전하지만 검증을 통과하지 못하는 프로그램을 만들 수 있다.

반대편 오류는 훨씬 위험하다.

실제 가능한 상태를 추상상태에서 누락하는 과소근사는 위험한 프로그램을 안전하다고 수락하는 거짓 음성(false negative)을 만들 수 있다.

검증기를 설계할 때는 두 목적이 충돌한다.

범위를 넓게 잡으면 보수적이지만 프로그램이 많이 거절되고, 범위를 정교하게 줄이면 편리하지만 추상연산 구현이 어려워진다.

좋은 검증기는 안전성을 훼손하지 않는 범위에서 정확도(precision)를 높여야 한다.

4. 메모리 경계검사를 손으로 따라가 보자

[교육용 가정]

패킷 데이터의 길이가 정확히 64바이트이고, offset \(o\)에서 4바이트 정수를 읽으려 한다.

유효 인덱스는 0~63이므로 안전조건은

0\le o

그리고

o+4\le64

다.

따라서

\boxed{0\le o\le60}

이어야 한다.

\(o=60\)이면 60·61·62·63을 읽으므로 안전하다.

\(o=61\)이면 64번 인덱스를 포함하므로 범위를 벗어난다.

단순화한 의사코드는 다음과 같다.

// 설명용 의사코드
// 실제 eBPF API나 컴파일 가능한 완성 예제는 아님

if (o > 60)
    return REJECT;

value = load_u32(data + o);

정적 분석기가 분기 이후

o\in[0,60]

을 알고 있다면 읽기를 허용할 수 있다.

하지만 부호가 있는 정수와 없는 정수를 혼동하거나 덧셈 오버플로를 무시하면 계산된 범위와 실제 주소가 달라진다.

그래서 커널 검증기는 단순한 최소·최댓값뿐 아니라 signed/unsigned 범위, 포인터 종류, 고정·가변 offset, 정렬상태까지 추적한다. Kernel.org

5. tnum: 비트 단위로 모르는 값을 표시하는 방법

Linux 공식 검증기 문서는 비트별 불확실성을 표현하는 tnum(tristate number) 을 설명한다.

tnum은

(value,mask)

형태다.

mask 비트가 1이면 그 위치는 미지수이고, mask가 0이면 value 비트가 0인지 1인지 확정됐다.

예를 들어 8비트에서

value = 0x40
        0100 0000

mask  = 0x0F
        0000 1111

라면 가능한 값은 0x40~0x4F, 즉 십진수 64~79다.

상위 네 비트는 확정됐지만 하위 네 비트는 모른다는 뜻이다.

구간 추상화와 tnum은 서로 보완적이다.

구간은 대소관계에 강하고 tnum은 비트마스크·정렬조건에 강하다.

여러 추상도메인이 정보를 주고받는 과정이 복잡해지는 만큼, 그 변환 자체가 검증기 오류의 원천이 될 수 있다. 리눅스 커널 아카이브

6. 분기가 늘면 가능한 상태가 폭발한다

분기 \(n\)개가 모두 독립적이면 경로 수는 이론적으로 최대

2^n

이다.

\(n=20\)이면

2^{20}=1,048,576

개다.

물론 실제 프로그램에서는 불가능한 분기와 조기에 합쳐지는 상태가 많다.

검증기는 같은 명령위치에서 이전에 안전하다고 검증한 추상상태와 새 상태를 비교해 불필요한 재탐색을 줄인다.

이를 state pruning이라고 한다.

간단한 예로 이전에

r\in[0,10]

인 상태에서 남은 코드가 안전함을 증명했고, 새로 도착한 상태가

r\in[2,4]

라고 하자.

다른 레지스터·스택·포인터 조건도 적절히 포함관계를 만족한다면 새 상태는 이전 상태의 부분집합이므로 후속 코드를 반복 검증하지 않아도 된다.

이 최적화의 전제는 추상상태가 올바르다는 것이다.

포함관계를 잘못 판단한 pruning은 위험한 실행경로를 검토에서 통째로 제외할 수 있다.

성능 최적화가 검증의 건전성과 직접 결합되는 지점이다. Linux Kernel Documentation

여기서 문서 읽기의 함정도 있다.

Linux 공식 verifier 설명의 서두는 여전히 루프를 전부 금지하는 초기 설계를 묘사하지만, 실제 Linux는 5.3부터 검증 가능한 bounded loop를 지원한다.

커널 문서는 설명문 일부가 오래됐을 수 있으므로 기능의 도입시점과 대상 커널 버전을 함께 봐야 한다. Kernel.org

7. 중심 논문이 겨냥한 문제: 검증기가 틀렸는지 어떻게 알까

일반적인 fuzzing은 프로그램에 다양한 입력을 넣고 crash나 명백한 예외를 찾는다.

그런데 검증기의 내부 범위 계산이 틀렸더라도 간단한 테스트 프로그램 자체는 멀쩡히 실행될 수 있다.

이때 검증기가 “안전하다”고 말한 것이 맞는지 자동으로 판정할 테스트 오라클(test oracle) 이 부족하다.

Sun과 Su의 핵심 관찰은 다음과 같다.

실제 실행에서 도달한 구체상태 \(s\)는 올바른 검증기의 그 지점 추상상태 \(A\)에 반드시 포함돼야 한다.

\boxed{s\in\gamma(A)}

따라서 이 포함관계를 검증기 자신에게 질문하는 프로그램을 만들면 된다. USENIX

8. State embedding의 작동 원리

먼저 원래 프로그램 \(P\)가 검증기에 수락됐다고 하자.

이를 실행해 어떤 명령지점의 실제 레지스터 값

r=12

를 관측한다.

같은 지점에 다음과 같은 개념적 검사 코드를 삽입한 \(P'\)를 만든다.

// 개념적 테스트
// 의도적으로 무효한 동작을 포함한다.

if (r == 12) {
    verifier_sink();
    // 정적 검증기가 반드시 거절해야 할 동작
}

올바른 검증기는 실제로 발생한 \(r=12\)를 가능한 값으로 남겨야 한다.

따라서 위험한 sink로 들어가는 경로를 고려하고 \(P'\)를 거절해야 한다.

그런데 검증기 버그가

r\in[0,7]

이라고 잘못 추정했다면

r==12

를 불가능한 분기로 처리하고 sink를 건너뛰어 \(P'\)를 수락할 수 있다.

이때 원래 \(P\)가 안전하게 실행됐다는 사실과, 삽입한 \(P'\)를 수락했다는 사실 사이의 모순이 검증기 논리오류를 드러낸다.

논문의 실제 도구 SEV는 레지스터별 관측값을 하나의 값으로 접는(folding) 절차, 런타임 프로파일링, 변형 프로그램 생성, 검증기 재실행을 사용한다.

위 코드는 그 핵심 논리를 이해하기 위한 축약이며 논문 구현 전체가 아니다. USENIX

9. 실제로 찾아낸 오류: -1을 저장했는데 다른 수로 기억했다

논문 §2.2의 사례에서는 32비트 signed immediate \(-1\)을 64비트 스택 슬롯에 기록하는 과정의 부호 확장(sign extension) 처리가 잘못됐다.

올바른 64비트 2의 보수 표현은

0xFFFFFFFFFFFFFFFF

이다.

그런데 당시 검증기 내부 코드가 중간에 u32로 캐스팅하면서 상위 32비트의 부호정보를 잃어 추적값을

0x00000000FFFFFFFF

처럼 다르게 기록했다.

실제 실행과 검증기의 기억이 어긋난 것이다.

연구진은 이 문제를 찾아 수정 패치를 제시했고, 논문에는 upstream 병합 및 stable kernel backport가 보고돼 있다.

같은 논문은 발견된 오류 중 두 개가 해당 실험에서 권한상승에 악용 가능했다고 보고한다.

재현조건은 특정 권한·커널 설정에 의존하므로 “모든 Linux 사용자에게 같은 공격이 가능하다”는 뜻으로 읽으면 안 된다.

이 사례가 중요한 이유는 단순한 캐스팅 실수가 보안 경계의 잘못된 증명으로 이어질 수 있다는 점이다. USENIX

13

10. 연구 성과를 어떻게 해석해야 하나

원논문은 실제 Linux eBPF verifier를 대상으로 한 달 동안 테스트했고 새 논리오류 15개 발견, 논문 제출 당시 10개 수정을 보고했다.

이는 저자들의 실험과 bug triage에 대한 보고다.

하지만 “15개를 발견했다”는 것은 전체 버그 수를 측정했다는 뜻도, 이후 kernel에서 같은 결함이 여전히 남아 있다는 뜻도 아니다.

또한 발견하지 못한 프로그램까지 모두 안전하다고 증명한 것도 아니다.

State embedding의 강점은 기존 검증기의 추상화 불변식을 테스트 가능한 관계로 만든 데 있다.

한편 프로파일링에서 관측하지 못한 상태는 이 방법만으로 시험하지 못한다.

따라서 전수 수학적 증명보다 강력한 오류 탐지·회귀검증 기법으로 보는 편이 정확하다. USENIX

14

11. 2025~2026년 흐름: '검증기가 틀릴 수 있다'를 설계에 반영한다

같은 연구진의 2025년 USENIX Security 논문 「Approximation Enforced Execution of Untrusted Linux Kernel Extensions」는 더 나아간다.

검증기의 근사가 틀릴 가능성을 인정하고, 실제 실행이 추상상태를 벗어나면 런타임에 차단하도록 하는 AEE(Approximation-Enforced Execution) 개념이다.

저자들은 공간적 메모리 안전성에 초점을 둔 시제품에서 trusted code base를 4.5배 줄이고, 평균 실행 오버헤드 1.2%, 바이너리 크기 증가 4.8%를 보고했다.

이는 해당 연구의 프로토타입 결과이며 모든 eBPF 프로그램의 공통 수치가 아니다. USENIX

2026년 프리프린트 「Heimdall: Formally Verified Automated Migration of Legacy eBPF Programs to Rust」는 또 다른 빈틈을 지적한다.

커널 검증기를 통과한 코드라도 이벤트 기록의 일부 필드를 초기화하지 않거나, helper 반환값을 잘못 처리하거나, 출력 스키마를 잘못 사용하는 상위 수준의 의미적 오류는 남을 수 있다.

연구진은 C 기반 eBPF 코드를 Rust로 옮기고 기호실행과 SMT 기반 동등성 검사를 결합했다.

102개 프로그램 중 96개의 변환에 대해 보고된 조건 아래 동등성을 입증했다고 주장한다. 프리프린트이므로 후속 검증이 필요하다. arXiv

결국 안전은 하나의 검증기가 떠맡는 속성이 아니라 언어·컴파일러·검증기·런타임·테스트·운영정책이 겹쳐 만든 성질이다.

15

12. 여러 분야에 통하는 구조적 교훈

형식논리 렌즈: 검증기의 주장은 “가능한 실제 상태가 이 추상적 울타리 안에 모두 있다”는 전칭명제다.

반례 하나가 있으면 증명이 깨진다. 따라서 반례를 체계적으로 만드는 테스트가 강력하다.

보안경제학 렌즈: 실행할 때마다 모든 메모리 접근을 검사하는 것은 비용이 크다. eBPF는 많은 검사를 적재 시점으로 옮겨 실행경로 비용을 줄인다.

이것은 검증 부담을 없앤 것이 아니라 런타임에서 배포 이전으로 이전한 것이다. 검증기가 시스템의 병목이자 단일 실패지점이 되는 반대급부가 생긴다.

품질관리 렌즈: 정상 프로그램을 여러 개 통과시키는 테스트만으로 안전성이 입증되지 않는다.

어떤 검증결과가 나왔을 때, 그 결과를 반박할 수 있는 오라클과 변형 테스트(metamorphic testing) 가 필요하다.

본 사례에서 '수락된 프로그램의 실제 상태는 검증기의 추상상태에 포함돼야 한다'가 바로 그런 검증가능한 관계다.

인센티브·조직 렌즈: 검증기가 지나치게 엄격하면 개발자는 더 복잡한 우회 구현을 만들려 한다.

지나치게 관대하면 보안위험이 증가한다.

개발생산성, 성능, 거절률, 취약점 수를 하나의 KPI로 환원하면 위험하다. 검증 가능한 안전조건의 범위와 정상 코드 거절률을 분리해 측정해야 한다.

AI 코드생성 렌즈: LLM이 생성한 eBPF 프로그램이 컴파일되고 verifier를 통과했다고 해서, 요구사항대로 작동한다는 뜻은 아니다.

하위 수준의 안전성 검사와 상위 수준의 요구사항·데이터 유출·출력정합성 검사는 서로 다른 층이다.

생성 AI를 개발과 검증에 쓰더라도 '검증 통과'를 '업무 정답'으로 승격시키면 안 된다.

3. 「Approximation Enforced Execution of Untrusted Linux Kernel Extensions」

저자: Hao Sun·Zhendong Su
발표: USENIX Security 2025, 2025년 8월.

검증기 버그를 발견하는 데서 한 걸음 더 나아가, 검증기 근사가 틀릴 때도 런타임에서 차단하는 방어설계를 연구한다.

논문의 'approximation enforcement'와 reduced trusted code base의 의미를 살펴보며 '적재 전 검증과 실행 중 검사의 최적 분담은 무엇인가?'를 생각하라.

예상 학습시간: 40~50분. USENIX

Approximation Enforced Execution — USENIX Security 2025

PAUSE & REFLECT

잠깐, 내 언어로 설명해 보기

Q1.

어떤 레지스터가 실제로

0\sim255

의 값을 가질 수 있다.

r = r & 15;

이후 분석기가

[0,15]

라고 추정하는 것과

[0,7]

이라고 추정하는 것 가운데 어느 것이 건전한가?

구체값 \(r=12\)로 설명하라.

해설 보기 +

r&15는 8비트 값의 하위 네 비트만 남기므로 결과집합은 0~15다.

[0,15]

는 가능한 값을 모두 담아 건전하다.

반면 \(r=12\)이면 결과도 12인데

[0,7]

에는 포함되지 않으므로 과소근사이며 건전하지 않다.

Q2.

64바이트 버퍼에서 4바이트를 읽을 때 허용 가능한 시작 offset의 최댓값은 얼마인가?

o\le61

이라는 검사에는 어떤 오류가 있는가?

또 검증기가 특정 명령위치에서 이전 상태

[0,10]

을 안전하게 검증했다면 현재 상태

[2,4]

를 재검증하지 않아도 되는 조건을 설명하라.

해설 보기 +

마지막으로 읽는 인덱스는

o+3

이므로

o+3\le63

즉

\boxed{o\le60}

이다.

\(o=61\)은 인덱스 61~64를 접근하므로 잘못됐다.

Pruning은 새 상태가 이전에 안전성이 증명된 상태의 부분집합이고, 레지스터 외에도 포인터 종류·스택·추적된 생존상태 및 후속 실행조건이 호환되는 경우에만 정당하다.

Q3.

정상 실행에서

r=12

가 관측됐는데 검증기는 그 지점을

[0,7]

이라고 추정했다.

if (r == 12)
    verifier_sink();

를 삽입한 프로그램을 검증기가 수락했다면, 무엇이 잘못됐는가?

이 테스트 하나만으로 전체 검증기의 안전성을 증명할 수 없는 이유도 설명하라.

해설 보기 +

실제값 12가 검증기의 근사 [0,7]에 누락됐다.

올바른 검증기라면 조건이 가능한 것으로 판단하고 의도적으로 무효한 sink 때문에 프로그램을 거절해야 한다.

수락한다면 추상상태의 건전성에 문제가 있다는 강한 신호다.

하지만 관측하지 못한 실행상태, 다른 명령, 다른 환경의 버그까지 모두 탐지한 것은 아니므로 보편적 안전성 증명은 아니다.
