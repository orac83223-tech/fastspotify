02

오늘의 질문: RDB 품질관리를 잘하는데도 왜 온톨로지가 필요한가?

오늘 비교한 세 후보는 ① RDB 데이터품질을 잘 관리하고 있는데도 왜 온톨로지가 필요한가, ② RAG가 semantic search라면 GraphRAG·ontology는 어디서 추가 가치를 만드는가, ③ AI 에이전트가 기업 업무를 수행하려면 데이터 카탈로그가 ‘설명서’에서 ‘행동 가능한 모델’로 어떻게 바뀌어야 하는가였습니다. 최근에는 장기기억·코드 검증·Physical AI를 다뤘기 때문에 오늘은 데이터 품질과 ontology를 하나의 구조로 묶었습니다.

핵심 통찰은 이렇습니다. RDB 데이터품질은 주로 “값이 구조적으로 올바른가”를 보장하고, 온톨로지는 “그 값이 현실 세계에서 무엇을 뜻하며 다른 개념과 어떤 관계를 갖는가”를 명시합니다. 둘은 대체재가 아니라 서로 다른 층입니다. AI 시대에는 여기에 한 층이 더 붙습니다. “그 의미를 바탕으로 어떤 행동이 허용되는가”까지 모델링해야 에이전트가 안전하게 업무를 수행할 수 있습니다.

03

1. RDB가 완벽해도 의미는 틀릴 수 있다

가상의 기업 시스템을 생각해 보겠습니다.

CUSTOMER_ID는 NOT NULL이고 PK가 유일합니다. CONTRACT.CUSTOMER_ID에는 FK가 걸려 있습니다. 날짜 형식도 맞고 코드값도 코드 테이블에 존재합니다. 데이터품질 진단을 돌리면 100점에 가까울 수 있습니다.

그런데 시스템 A에서 CUSTOMER가 계약을 신청한 사람, 시스템 B에서 CUSTOMER가 실제 서비스를 사용하는 사람, 시스템 C에서 CUSTOMER가 비용을 납부하는 사람을 뜻한다면 어떻게 될까요?

각 테이블 내부에서는 아무 문제도 없습니다. 문제는 같은 단어가 서로 다른 현실의 역할(role)을 가리킨다는 것입니다.

이 오류는 NOT NULL, PK, FK, CHECK로 잡기 어렵습니다.

관계형 데이터 품질을 세 층으로 나누면 다음처럼 볼 수 있습니다.

1층 — 구조적 품질: 형식, 타입, NULL, 범위, PK/FK, 중복.

2층 — 의미적 품질: “고객”, “계약”, “승인”, “변경”이 조직 전체에서 무엇을 뜻하는가.

3층 — 운영적 품질: 어떤 상태에서 어떤 행동을 누가 수행할 수 있으며, 그 행동 뒤 상태가 어떻게 바뀌어야 하는가.

RDB는 1층에 매우 강합니다. 온톨로지는 주로 2층을 다루고, 최근의 enterprise ontology는 3층까지 확장하는 방향입니다.

04

2. 온톨로지는 ‘그래프로 저장하는 것’과 다르다

Graph DB는 저장·탐색 구조입니다.

Knowledge Graph는 현실의 entity와 relation을 그래프로 표현한 데이터입니다.

Ontology는 그 그래프에 들어갈 개념의 종류, 관계의 의미, 제약과 추론 규칙을 정의하는 모델입니다.

W3C의 OWL 2는 ontology에 class, property, individual과 formal semantics를 부여합니다. 즉 Employee, Contract, Claim 같은 개념이 무엇이고 서로 어떤 관계를 가질 수 있는지를 컴퓨터가 추론 가능한 형태로 표현합니다. (W3C) W3C OWL 2 Primer

그래서 그래프에 A —related_to→ B라고 연결했다고 해서 자동으로 ontology가 되는 것은 아닙니다. related_to가 고용관계인지, 계약관계인지, 소유관계인지, 시간에 따라 바뀌는 관계인지, 역관계가 무엇인지가 정의되어야 의미가 생깁니다.

데이터베이스로 비유하면 Graph DB가 저장엔진이라면 ontology는 schema + domain model + 일부 business semantics에 가깝습니다.

05

3. semantic search와 ontology의 차이는 ‘비슷함’과 ‘참임’의 차이다

RAG의 semantic search는 질문과 의미가 비슷한 문서 조각을 embedding 공간에서 찾아 LLM에게 넣습니다.

하지만 semantic similarity는 기본적으로 “이 문장과 저 문장이 얼마나 비슷한가?”를 다룹니다.

ontology는 다른 질문을 합니다.

“A는 B의 하위개념인가?”

“이 관계의 주체와 객체는 어떤 타입이어야 하는가?”

“이 두 표현은 같은 개체인가?”

“이 상태에서는 이 행동이 허용되는가?”

semantic search가 후보 증거를 찾는 엔진이라면 ontology는 그 증거가 어떤 업무 개념에 속하는지 해석하는 좌표계에 가깝습니다.

그래서 RAG와 ontology는 경쟁하지 않습니다.

Vector Search → 관련 텍스트
Knowledge Graph → 관련 객체와 관계
Ontology → 관계의 의미와 허용 규칙
LLM → 현재 질문에 맞는 추론과 설명

Microsoft GraphRAG도 entity·relationship·claim을 추출해 knowledge graph와 community summary를 만들고 vector embedding도 함께 사용합니다. 즉 ‘vector를 버리고 graph로 간다’기보다 서로 다른 retrieval 구조를 조합하는 접근입니다. (GitHub) Microsoft GraphRAG 개요

06

4. 데이터품질에서 ontology가 특히 강해지는 지점은 ‘cross-system consistency’다

테이블 하나의 품질은 SQL로 상당 부분 검사할 수 있습니다.

문제는 시스템이 많아질 때입니다.

시스템마다 CUST_NO, CLIENT_ID, USER_ID, CUSTOMER_KEY처럼 서로 다른 식별자를 쓰면 이들이 같은 현실 개체를 가리키는지, 아니면 서로 다른 역할을 표현하는지 판단해야 합니다.

이때 품질 규칙은 column rule에서 concept rule로 올라갑니다.

예를 들어 ontology에서 Person, Organization, ContractParty, Payer, User, Beneficiary를 분리하고, Payer is-a ContractParty처럼 정의한다고 생각해봅시다.

각 시스템의 컬럼을 이 개념에 매핑하면 “컬럼명은 다르지만 같은 개념”과 “컬럼명은 같지만 다른 개념”을 구분할 수 있습니다.

그 순간 데이터품질은 ‘컬럼 X의 NULL 비율’에서 “우리 회사 전체에서 특정 개념이 일관되게 구현돼 있는가?”라는 질문으로 올라갑니다.

이것이 ontology가 데이터 표준·메타데이터·데이터품질과 연결되는 핵심입니다.

07

5. OWL만으로 데이터품질 검증을 끝내면 안 된다

고전적인 관계형 DB는 대체로 Closed World 방식으로 생각합니다. DB에 값이 없으면 ‘없다’고 취급하기 쉽습니다.

반면 OWL의 형식 의미론은 기본적으로 Open World입니다. 어떤 사실이 기록돼 있지 않다고 해서 그 사실이 거짓이라는 뜻은 아닙니다. OWL은 RDF 위에 형식 의미론을 제공해 명시된 사실로부터 논리적 함의를 다루는 쪽에 초점이 있습니다. (W3C)

실무 데이터품질에서는 “계약에는 반드시 계약일자가 있어야 한다”처럼 정보가 없으면 명시적으로 오류로 잡아야 하는 경우가 많습니다.

그래서 RDF 생태계에는 SHACL(Shapes Constraint Language)이 있습니다. SHACL은 RDF graph가 정해진 shape와 조건을 만족하는지 검증하기 위한 W3C 표준입니다. (W3C) W3C SHACL Recommendation

실무적으로는 이렇게 분리하는 편이 좋습니다.

OWL → 무엇이 논리적으로 성립하는가

SHACL → 데이터가 요구조건을 만족하는가

RDB Constraint → 저장 시점에 무엇을 허용할 것인가

08

6. 2026년 연구는 ‘LLM이 ontology를 없앤다’보다 ‘ontology를 만드는 비용을 낮춘다’ 쪽으로 가고 있다

ontology의 약점은 만들기가 비싸다는 것입니다. 도메인 전문가와 데이터 모델러가 개념을 정의하고 관계와 계층을 맞춰야 합니다.

2026년 IEEE ICSC에 발표된 OntoEKG는 LLM으로 enterprise ontology 구축을 자동화하려는 사례입니다. 문서에서 class와 property를 추출하고, entailment 단계에서 hierarchy를 구성한 뒤 RDF로 직렬화합니다. 저자 실험에서 Data domain fuzzy-match F1은 0.724였지만 scope 정의와 계층적 reasoning에서 한계가 나타났습니다. (DOI) IEEE — LLM-Driven Ontology Construction for Enterprise Knowledge Graphs

이 결과는 LLM이 ontology engineer를 없앤다기보다

LLM → 후보 개념·관계 생성

전문가 → 의미·경계·예외 검증

검증 규칙 → 자동 품질검사

라는 구조가 현실적임을 시사합니다.

코드 생성이 싸질수록 code review와 oracle이 중요해지는 것과 같은 패턴입니다. 의미 생성 비용은 내려가지만, 정답 의미를 승인하는 책임은 남습니다.

09

7. 불과 2주 전 Apple이 공개한 Glyph는 ontology와 데이터품질이 만나는 현실적인 사례다

Apple Machine Learning Research가 2026년 9월 공개한 Glyph는 enterprise data catalog의 column description과 sensitivity classification을 자동화하는 production system입니다.

Descriptor agent는 해당 컬럼을 생성하는 pipeline source code를 찾아 설명을 grounding하고, Tagger는 275개의 leaf category를 가진 governed Data Classification Ontology에서 라벨을 선택합니다. description, regex/line-of-business metadata, fine-tuned encoder의 세 전략을 병렬로 사용하고 결과를 fusion하며 각 tag에 provenance를 남기는 구조를 강조합니다. (Apple Machine Learning Research) Apple Machine Learning Research — Glyph

이 사례가 중요한 이유는 ontology가 거창한 ‘AI 지식그래프’보다 먼저 데이터 카탈로그 품질에서 실용적일 수 있다는 점입니다.

예전 방식:
COLUMN_NAME → 사람이 설명

새 구조:
Pipeline Code + Metadata + Domain Ontology → 설명 + 분류 + 근거

즉 메타데이터 관리가 단순 문서화에서 자동 검증 가능한 semantic governance로 이동합니다.

10

8. enterprise ontology는 고전적 ontology보다 ‘행동’을 품기 시작했다

Palantir가 ontology라는 단어를 사용하는 방식은 W3C OWL과 구분해서 봐야 합니다.

W3C ontology는 formal semantics가 중심입니다.

Palantir의 Ontology는 훨씬 운영체제에 가까운 개념으로, 공식 문서에서 object type, link type뿐 아니라 action type, function, security까지 하나의 operational model로 묶습니다. Palantir 공식 설명은 이를 data, logic, action, security의 통합으로 표현합니다. (Palantir) Palantir Ontologies Overview Palantir Action Types Overview

전통 knowledge graph가

Object —ownedBy→ Team

을 표현한다면 operational ontology는

ApproveObject(actor, object)

같은 행동을 정의하고 누가 실행 가능한지, 실행하면 어떤 상태가 바뀌는지, 어떤 보안정책을 통과해야 하는지까지 포함합니다.

AI agent에게 이것은 매우 중요합니다. LLM이 “무엇이 무엇과 관련 있는지” 아는 것만으로는 업무를 맡길 수 없습니다. 무엇을 해도 되는지를 알아야 합니다.

그래서 장기적으로 enterprise AI의 semantic layer는

Entity + Relation + State + Action + Policy + Provenance

로 확장될 가능성이 큽니다.

11

9. 가장 강한 반론: ontology는 너무 비싸고, 결국 또 하나의 ‘문서 부채’가 되지 않는가?

맞는 반론입니다.

ontology project가 실패하는 전형적인 방식은 현실 전체를 완벽하게 모델링하려는 것입니다. 수백 개 class와 수천 개 relation을 만든 뒤 현업 시스템은 계속 바뀌고 ontology는 업데이트되지 않습니다.

그러면 ‘single source of truth’가 아니라 또 하나의 오래된 truth가 됩니다.

특히 데이터가 단순하고 질문이 대부분 단일 테이블 aggregation이라면 SQL과 data catalog만으로 충분합니다.

Ontology가 경제성을 갖는 지점은 대체로 세 조건이 겹칠 때입니다.

첫째, 같은 개념이 여러 시스템에 흩어져 있다.

둘째, 관계를 여러 hop 따라가야 답할 수 있다.

셋째, 사람 또는 AI가 그 의미를 바탕으로 실제 행동까지 해야 한다.

이 세 가지가 없다면 ontology는 과잉설계일 수 있습니다.

12

10. 현실적인 도입 순서는 ‘전사 ontology 구축’이 아니라 작은 semantic control loop다

가장 좋은 시작은 거대한 knowledge graph가 아닐 가능성이 큽니다.

업무 하나를 고르고 핵심 object만 정의합니다. 예를 들어 ChangeRequest, Program, Approver, TestResult, Deployment, Incident를 정의합니다.

그 다음 핵심 relation을 정의합니다.

ChangeRequest modifies Program
ChangeRequest has TestResult
Deployment implements ChangeRequest
Incident relatedTo Deployment

그 다음 품질 rule을 붙입니다.

“운영배포된 ChangeRequest에는 승인과 테스트결과가 존재해야 한다.”

마지막으로 action을 정의합니다.

ApproveChange
DeployChange
RollbackDeployment

이 작은 구조만으로도 SQL 품질진단, 변경통제, 테스트 증적, AI 질의응답을 하나의 의미체계로 묶을 수 있습니다.

핵심은 ontology를 먼저 만들고 업무를 끼워 맞추는 것이 아니라, 반복적으로 판단이 어려운 업무를 골라 ontology를 그 판단의 공통 언어로 만드는 것입니다.

13

11. 투자·전략 렌즈로 보면 ‘그래프DB’보다 semantic control plane이 더 중요한 개념일 수 있다

AI가 SQL도 만들고 문서도 검색하고 API도 호출할 수 있게 되면 단순한 데이터 접근 자체는 점점 싸집니다.

그럴수록 비싸지는 것은

같은 Customer가 무엇인지

어떤 상태가 유효한지

어떤 행동이 허용되는지

그 판단의 근거가 어디서 왔는지

를 관리하는 층입니다.

검색이 싸질수록 ‘검색된 정보의 의미를 통제하는 체계’가 상대적으로 중요해집니다.

다만 “ontology 시장이 커진다 → graph DB 업체가 모두 큰 해자를 가진다”는 결론은 성립하지 않습니다. ontology는 저장엔진이 아니라 조직의 domain model에 가깝기 때문입니다.

경제적 해자는 특정 graph technology보다 업무모델에 얼마나 깊게 박혀 있는가, 원천 데이터와 얼마나 잘 연결되는가, action과 policy까지 연결되는가, 변경 이력과 provenance를 얼마나 신뢰할 수 있는가에서 생길 가능성이 큽니다.

14

제가 이 결론을 바꿀 관측

LLM이 raw RDB schema와 문서만으로도 서로 다른 시스템의 개념 차이, temporal role, business rule을 안정적으로 추론하고, 별도의 governed ontology 없이 장기간 동일한 의미를 유지하며, 데이터 변경 후에도 hallucination이나 semantic drift 없이 자동 적응한다면 ontology의 필요성은 크게 줄어듭니다.

반대로 ontology를 붙인 시스템이 같은 RDB·같은 LLM 조건에서 cross-system 질의 정확도, 규칙 위반 탐지, agent tool-call 성공률, 감사 가능성, 변경 후 오류율을 지속적으로 개선한다면 ontology는 ‘옛날 Semantic Web 기술’이 아니라 AI가 기업 데이터를 안전하게 사용하는 control plane으로 다시 평가해야 합니다.

15

오늘 5~10분 실험

테이블 하나를 골라 컬럼 5개만 적어보세요.

그리고 각 컬럼에 세 질문을 붙입니다.

1. 이 값의 타입은 무엇인가?
→ RDB가 잘 답합니다.

2. 이 값은 현실 세계의 어떤 개념을 뜻하는가?
→ ontology가 필요한 영역입니다.

3. 이 값이 특정 상태일 때 어떤 행동이 허용되는가?
→ operational ontology와 policy의 영역입니다.

예를 들어 STATUS='03'이라는 컬럼을 보면 데이터베이스는 '03'이 유효한 코드인지 확인할 수 있습니다.

하지만

03 = 승인완료
승인완료 상태에서는 다음 단계 실행 가능
단, 예외 변경은 다른 승인경로 필요

까지 가면 이미 단순 column quality를 넘어 업무 의미의 품질을 다루고 있습니다.

여기가 RDB 데이터품질과 ontology가 만나는 정확한 지점입니다.

오늘의 영상

오늘은 후보군을 확장해 Palantir 공식 채널의 「AIP 2026: The Self-Healing Autonomous Enterprise | Paragon 2025」를 추천합니다. 2025년 12월 15일 공개된 영상으로, Ontology를 단순 knowledge graph가 아니라 enterprise의 데이터·프로세스·agent action을 연결하는 운영 구조로 보는 시각을 구체적으로 보여줍니다. (유튜브) AIP 2026: The Self-Healing Autonomous Enterprise | Paragon 2025 — Palantir Palantir Ontology System 공식 문서

영상 검증 상태: Palantir 공식 YouTube 채널의 영상 제목·게시일·설명을 확인했고, Ontology의 object/link/action/function 구조는 Palantir 공식 문서로 교차 확인했습니다. 다만 이 영상은 Palantir 자사 제품 발표이므로 성능이나 경제적 효과를 독립적인 실증 근거로 사용하지 않았습니다. 오늘 글의 ontology 표준 부분은 W3C, 최신 데이터 카탈로그 사례는 Apple Machine Learning Research, 자동 ontology 구축의 한계는 2026 IEEE ICSC 논문으로 별도 검증했습니다.

17

오늘 남길 문장

RDB 품질관리는 ‘데이터가 규칙에 맞는가’를 묻고, 온톨로지는 ‘그 데이터가 현실에서 무엇을 뜻하는가’를 묻는다. AI가 행동하기 시작하면 둘 사이의 연결이 곧 통제 시스템이 된다.
