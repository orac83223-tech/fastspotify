FlashAttention-4와 병목 이동: Tensor Core가 빨라졌는데 왜 softmax의 `exp`가 새 병목이 되는가

02

핵심 질문과 결론

핵심 질문: Transformer attention의 수학식은 그대로인데, 왜 A100 시대에는 HBM 왕복을 줄이는 것이 중요했고, H100에서는 비동기 파이프라이닝이 중요했으며, B200에서는 softmax의 exponential unit과 shared-memory traffic이 새 병목으로 떠올랐을까? 또 FLOPs가 줄지 않거나 일부 재계산이 늘어도 실제 wall-clock은 왜 더 빨라질 수 있을까?

결론: FlashAttention 계열의 핵심은 attention을 근사하는 것이 아니라 같은 attention을 GPU의 메모리 계층과 실행 유닛에 맞게 다른 순서로 계산하는 것이다. 2022년 FlashAttention은 \(N\times N\) attention matrix를 HBM에 materialize하지 않고 tile 단위로 처리해 I/O를 줄였다. 2026년 FlashAttention-4(FA4)는 Blackwell B200에서 Tensor Core 처리량은 크게 증가했지만 exponential unit과 shared-memory bandwidth는 같은 속도로 늘지 않았다는 비대칭 하드웨어 스케일링을 직접 겨냥한다. FA4는 matmul과 softmax를 겹쳐 실행하고, exp 일부를 FMA 기반 다항식으로 옮기며, Tensor Memory와 2-CTA MMA를 활용해 shared-memory traffic을 줄인다. 논문은 B200 BF16에서 최대 1613 TFLOPs/s, theoretical peak의 약 71%, cuDNN 9.13 대비 최대 1.3배, Triton 대비 최대 2.7배를 보고한다. 다만 저자들은 논문 이후 더 최신 cuDNN이 여러 기법을 흡수해 FA4와 비슷한 성능을 내기 시작했다고 함께 적었다. arXiv

오늘의 중심 원자료는 Ted Zadouri, Markus Hoehnerbach, Jay Shah, Timmy Liu, Vijay Thakkar, Tri Dao의 “FlashAttention-4: Algorithm and Kernel Pipelining Co-Design for Asymmetric Hardware Scaling”이다. arXiv 최초 공개는 2026-03-05, MLSys 2026 발표작이다. 오늘 2026-10-04 KST에 원문 PDF의 attention 수식, Blackwell 하드웨어 특성, forward/backward roofline 분석, exp 근사, online-softmax rescaling, benchmark 부분을 직접 확인했다. arXiv

03

1. Attention 수식을 먼저 복습하자

한 attention head에서

Q,K,V\in\mathbb{R}^{N\times d}

라 하자. \(N\)은 sequence length, \(d\)는 head dimension이다.

Score matrix는

S=\alpha QK^\top,
\qquad
\alpha=\frac1{\sqrt d}

이고,

P=\operatorname{softmax}(S),

최종 출력은

O=PV

다. 즉 forward attention은 크게

\boxed{
QK^\top
\rightarrow
\operatorname{softmax}
\rightarrow
PV
}

라는 큰 행렬곱 두 번과 가운데 softmax다. FA4 원문도 바로 이 수식에서 출발한다. arXiv

표준 attention 구현은 \(S\)와 \(P\)를 \(N\times N\) 형태로 HBM에 써놓고 다시 읽기 때문에 중간 메모리와 I/O가 크게 늘어난다. 원래 FlashAttention 논문은 이 \(N^2\) intermediate materialization을 피하는 것이 핵심이라고 설명한다. arXiv

여기서 첫 번째로 구분해야 할 것이 있다.

\boxed{
O(N^2)\text{ 연산량}
\neq
O(N^2)\text{ 중간 메모리를 반드시 저장해야 함}
}

이다.

FlashAttention은 모든 Query-Key pair 계산 자체를 없애지 않는다. 대신 그 결과를 느린 HBM에 전부 저장하지 않는다.

04

2. 4K context만 되어도 중간행렬은 꽤 크다

예를 들어

N=4096

이면

N^2=16{,}777{,}216.

BF16 한 원소가 2 byte라고 하면 \(N\times N\) 행렬 하나만 해도

16{,}777{,}216\times2
=
33{,}554{,}432\text{ bytes}

즉 약

32\text{ MiB}

다.

그런데 이것은 head 하나, \(S\) 하나만 계산한 수치다. 여러 head, batch, \(P\), backward를 위해 저장해야 하는 intermediate까지 생각하면 traffic은 훨씬 커진다.

그래서 FlashAttention의 중요한 질문은

FLOPs를 얼마나 줄일 수 있는가?

보다 먼저

같은 FLOPs를 하더라도 HBM과 on-chip memory 사이에 데이터를 몇 번 옮겨야 하는가?

였다.

2022년 FlashAttention 논문은 이 관점을 IO-awareness라고 불렀고, tile과 recomputation을 써서 HBM 왕복을 줄였다. 일부 FLOPs가 늘어나도 HBM access가 크게 줄면 실제 runtime은 더 빨라질 수 있다고 보고했다. arXiv

이는 9월 8일 배운 Roofline 모델과 정확히 연결된다.

05

3. 그런데 softmax는 전체 행을 보지 않고 어떻게 계산할까

Softmax 한 행의 score를

s_1,\dots,s_N

이라 하자.

수치적으로 안정한 softmax는

p_i=
\frac{e^{s_i-m}}
{\sum_j e^{s_j-m}},
\qquad
m=\max_j s_j

로 계산한다.

문제는 전체 행을 보기 전에는 \(m\)도 denominator도 모른다는 것이다.

그런데 FlashAttention은 이걸 online softmax로 해결한다.

지금까지 본 block의 통계를

m_{\text{old}}

= running maximum,

\ell_{\text{old}}

= running exponential sum,

o_{\text{old}}

= 아직 최종 normalize하지 않은 weighted-value numerator라고 하자.

새 block의 score를 \(s_{\text{new}}\), value를 \(V_{\text{new}}\)라 하면

m_{\text{new}}
=
\max
\left(
m_{\text{old}},
\max(s_{\text{new}})
\right)

이고

\ell_{\text{new}}
=
e^{m_{\text{old}}-m_{\text{new}}}
\ell_{\text{old}}
+
\sum
e^{s_{\text{new}}-m_{\text{new}}}.

또

o_{\text{new}}
=
e^{m_{\text{old}}-m_{\text{new}}}
o_{\text{old}}
+
\sum
e^{s_{\text{new}}-m_{\text{new}}}V_{\text{new}}.

모든 block을 끝내면

\boxed{
O=
\frac{o_{\text{final}}}
{\ell_{\text{final}}}
}

이다.

FA4도 이 running max와 running normalizer 구조를 사용하며, 원문 §3.1.4가 이 식을 명시한다. arXiv

06

4. 손계산: 두 block으로 나눠도 결과가 똑같다

[교육용 예제]

Score와 scalar value가

s=[1,2,3,0]
v=[10,20,30,40]

라고 하자.

전체 max는

m=3

이다.

따라서 stable exponential은

[e^{-2},e^{-1},1,e^{-3}]

즉 약

[0.1353,0.3679,1,0.0498]

이다.

분모는

\ell
=
0.1353+0.3679+1+0.0498
\approx1.5530.

분자는

o
=
0.1353(10)
+
0.3679(20)
+
1(30)
+
0.0498(40)
\approx40.7024.

따라서

O
\approx
\frac{40.7024}{1.5530}
=
26.2089.

이제 score를

[1,2]

와

[3,0]

두 block으로 나누자.

첫 block에서

m_1=2
\ell_1=e^{-1}+1
\approx1.3679
o_1=e^{-1}(10)+20
\approx23.6788.

두 번째 block의 최대값은 3이므로

m_2=3.

이전 결과를 새 max 기준으로 바꾸는 rescaling factor는

e^{2-3}=e^{-1}\approx0.3679.

따라서

\ell_2
=
0.3679(1.3679)+1+e^{-3}
\approx1.5530

이고

o_2
=
0.3679(23.6788)
+
30
+
e^{-3}(40)
\approx40.7024.

결국

\frac{o_2}{\ell_2}
\approx26.2089

다.

전체를 한 번에 계산한 결과와 같다.

이 덕분에 FlashAttention은 \(N\times N\)의 \(P\) 전체를 HBM에 저장하지 않고도 attention을 계산할 수 있다.

5. 그럼 2022 FlashAttention으로 문제가 끝난 것 아닌가

아니다.

GPU 자체가 변한다.

FA4 논문이 보여주는 중요한 변화는 하드웨어 각 부품의 성장률이 다르다는 점이다.

논문이 제시하는 B200의 SM당 대표 throughput은

8192

BF16 Tensor-Core ops/cycle/SM,

16

exponential ops/cycle/SM,

shared-memory read가

128\text{ bytes/cycle/SM}

이다. 또한 저자들은 H100에서 B200으로 가면서 FP16/BF16 Tensor Core peak가 GPU 기준 약 1 PFLOPS에서 2.25 PFLOPS로 커졌지만, exponential unit과 shared-memory bandwidth는 같은 비율로 증가하지 않았다고 분석한다. arXiv

이것이

\boxed{
\text{asymmetric hardware scaling}
}

이다.

08

6. GPU를 “하나의 계산기”로 보면 이 현상을 이해할 수 없다

GPU 내부에는 서로 다른 자원이 있다.

Tensor Core는 matrix multiply를 한다.

MUFU는 exponential 같은 특수함수를 처리한다.

Shared memory는 on-chip data movement를 담당한다.

FMA/ALU는 일반 arithmetic을 수행한다.

HBM은 대용량 데이터를 공급한다.

따라서

GPU가 2배 빨라졌다

라는 문장은 실제로는 정보가 부족하다.

무엇이 2배 빨라졌는가?

Tensor Core인가?

HBM인가?

Shared Memory인가?

SFU인가?

Interconnect인가?

이 비율이 workload의 병목을 결정한다.

09

7. 논문의 Roofline 계산을 직접 해보자

FA4는 forward tile의 Query 길이를 \(M\), Key 길이를 \(N\), head dimension을 \(d\)라 둔다.

Forward에는 두 MMA가 있다.

QK^\top

과

PV.

두 행렬곱의 총 연산량은

4MNd

이므로 B200 Tensor Core throughput을 적용하면 논문의 단순화된 계산시간은

\boxed{
T_{\text{MMA}}
=
\frac{4MNd}{8192}
}

cycles다. arXiv

Shared-memory read 시간은 \(M,N,d\)가 128의 배수라는 단순화에서

\boxed{
T_{\text{SMEM}}
=
\frac{3MNd}{8192}
}

이고,

softmax exponential은 \(MN\)개이므로

\boxed{
T_{\exp}
=
\frac{MN}{16}
}

이다. arXiv

이제

M=N=d=128

을 넣자.

128^3
=
2{,}097{,}152.

따라서

T_{\text{MMA}}
=
\frac{4(2{,}097{,}152)}{8192}
=
1024.
T_{\text{SMEM}}
=
\frac{3(2{,}097{,}152)}{8192}
=
768.
T_{\exp}
=
\frac{128^2}{16}
=
1024.

즉

\boxed{
T_{\text{MMA}}=1024
}
\boxed{
T_{\exp}=1024
}
T_{\text{SMEM}}=768

이다.

FA4 논문의 Table 1도 같은 값을 제시하며, MMA와 exponential unit이 forward의 주된 병목이라고 분석한다. arXiv

10

8. Tensor Core만 두 배 빠르게 하면 어떻게 될까

아주 단순한 교육용 모델로 세 작업이 완전히 순차 실행된다고 하자.

현재 총시간은

1024+768+1024
=
2816.

Tensor Core를 두 배 빠르게 해서

T_{\text{MMA}}=512

로 만들더라도

512+768+1024
=
2304.

Speedup은

\frac{2816}{2304}
\approx1.22.

Tensor Core가 두 배 빨라졌는데 전체는 약 1.22배밖에 빨라지지 않는다.

실제 FA4 kernel은 이처럼 단순히 합산되지 않고 여러 resource를 overlap하므로 이 숫자를 실측예측으로 쓰면 안 된다.

하지만 구조는 Amdahl의 법칙과 같다.

\boxed{
\text{이미 빠른 부품을 더 빠르게 해도
전체 시스템의 병목이 다른 곳이면 효과가 작다.}
}

11

9. 그래서 FA4는 “줄일 수 없으면 겹친다”

FA4의 첫 번째 핵심은 pipeline overlap이다.

두 Query tile을 번갈아 처리하면서 개념적으로

\text{Tile A: MMA}

하는 동안

\text{Tile B: softmax}

를 진행한다.

그 다음에는 역할이 바뀐다.

B200은 MMA가 fully asynchronous이고 결과를 TMEM에 쓸 수 있기 때문에 이런 overlap을 더 공격적으로 만들 수 있다. FA4는 Tensor Core, softmax warpgroup, data movement를 서로 다른 역할에 배치한다. arXiv

공장으로 비유하면 단순하다.

절단기 작업이 끝날 때까지 포장기를 세워놓는 대신

\text{제품 A 절단}
\parallel
\text{제품 B 포장}

을 한다.

전체 작업량을 줄이지 않아도 idle time을 줄이면 throughput은 올라간다.

12

10. Tensor Memory는 단순히 “메모리가 조금 더 생긴 것”이 아니다

Blackwell은 SM마다

256\text{ KB}

Tensor Memory(TMEM)를 도입했다.

FA4 원문에 따르면 TMEM은 Tensor Core intermediate 저장용 on-chip memory이고, MMA 결과를 register 대신 TMEM으로 비동기적으로 쓸 수 있다. arXiv

이게 중요한 이유는 register pressure 때문이다.

더 큰 tile을 사용하면 동시에 살아 있어야 하는 intermediate도 커진다.

Register가 부족해 spill이 나면 fast path가 다시 느린 memory path로 내려간다.

TMEM이 있으면

\text{더 큰 tile}
\text{더 깊은 pipeline}
\text{낮은 register pressure}

를 함께 노릴 수 있다.

즉 새로운 memory level은 capacity만 바꾸는 것이 아니라 가능한 scheduling algorithm 자체를 바꾼다.

13

11. `exp` 유닛이 혼잡하면 일반 FMA를 빌려 쓴다

Softmax에는 exponential이 필요하다.

B200/GB200에서 논문이 제시한 MUFU 처리량은

16\text{ ops/cycle/SM}

인데 Tensor Core는

8192\text{ ops/cycle/SM}

이다. 물론 두 연산의 의미가 다르므로 숫자를 단순비교할 수는 없지만, attention tile에서는 exp 시간이 MMA와 동급의 병목이 된다. arXiv

FA4는 그래서 exp 일부를 FMA로 옮긴다.

2^x
=
2^{\lfloor x\rfloor}
2^{x-\lfloor x\rfloor}.

정수부분

2^{\lfloor x\rfloor}

은 IEEE-754 exponent bit를 이용해 빠르게 만들고,

fractional part

f=x-\lfloor x\rfloor\in[0,1)

에 대해서는

2^f
\approx
p_0+p_1f+p_2f^2+p_3f^3+\cdots

처럼 polynomial approximation을 사용한다. arXiv

핵심은 전부 바꾸지 않는다는 것이다.

논문은 tile 설정에 따라 exp의 약

10\%-25\%

만 software-emulated path로 보내고 나머지는 MUFU를 사용한다. 전부 FMA로 보내면 register pressure와 latency가 오히려 문제가 될 수 있기 때문이다. arXiv

이는 전형적인 load balancing이다.

혼잡한 전문창구의 손님 일부를 남는 일반창구로 보내는 것이다.

14

12. 근사 exp를 쓰면 이제 “exact attention”이 아닌가

여기서는 exact라는 말을 조심해야 한다.

2022년 FlashAttention이 말한 exact attention은 sparse attention이나 low-rank approximation처럼 attention operator 자체를 근사하지 않는다는 뜻이었다. arXiv

하지만 GPU 계산은 처음부터 유한정밀도다.

FA4의 polynomial exponential은 별도의 numerical approximation을 추가한다.

논문은 \(2^x\) polynomial을 400만 개 random input에서 검증했다. Degree-3의 FP32 maximum relative error는 약

8.77\times10^{-5}

였고, BF16으로 반올림한 뒤 maximum relative error는 약

3.90\times10^{-3}

으로 hardware MUFU와 거의 같은 수준이었다. 저자들은 BF16 quantization error가 degree 3 이상에서는 polynomial approximation error보다 더 크며, degree-3 polynomial이 99% input에서 hardware 결과와 1 BF16 ULP 이내였다고 보고한다. arXiv

따라서 구분은 이렇다.

\boxed{
\text{attention 구조의 근사}
\neq
\text{finite-precision numerical approximation}
}

이다.

15

13. Online softmax도 매 block마다 완벽히 rescale할 필요는 없다

Online softmax에서 새 maximum이 발견되면 과거 accumulator를

e^{m_{\text{old}}-m_{\text{new}}}

로 rescale해야 한다.

FA4는 max 변화가 작으면 이 rescaling을 건너뛰고, 충분히 큰 변화가 있을 때만 수행한 뒤 최종 normalization에서 정확한 statistics를 사용한다. 논문은 threshold를 두어 중간 rescaling을 줄이고, 최종 \(m_{\text{final}},\ell_{\text{final}}\)로 normalization한다고 설명한다. arXiv

여기에는 매우 일반적인 알고리즘 패턴이 있다.

\boxed{
\text{중간 단계에서 invariant를 항상 즉시 복구할 필요가 없다면,
비싼 정합 작업을 지연시킬 수 있다.}
}

데이터베이스의 deferred constraint check, write buffering, lazy reconciliation과 비슷하다.

16

14. Forward와 backward의 병목도 다르다

Forward attention은 \(QK^\top\), softmax, \(PV\)라는 구조라 exp throughput이 중요하다.

Backward는 논문 기준 한 iteration에서 MMA가 다섯 번 들어가며 \(dQ,dK,dV\) 등을 계산한다. 이쪽에서는 shared-memory traffic과 atomic accumulation이 더 중요해진다. arXiv

FA4는 Blackwell의 2-CTA MMA를 활용한다.

두 CTA가 하나의 MMA를 협력해서 수행하고 operand를 나눠 staging하므로 shared-memory 중복 traffic을 줄일 수 있다. 저자들은 이 구조를 이용해 backward의 global atomic add 수도 절반으로 줄였다고 설명한다. arXiv

즉

\boxed{
\text{하나의 kernel 안에서도 phase마다 병목이 다르다.}
}

17

15. 실제 benchmark 숫자는 어떻게 읽어야 하나

FA4는 B200 GPU에서 BF16 input, sequence length 1K~32K, causal/non-causal, 여러 head dimension으로 측정됐다.

Forward에서 논문은

1.1\sim1.3\times

cuDNN 9.13 대비,

2.1\sim2.7\times

Triton 대비 속도향상을 보고한다.

전체 benchmark 중 최대는 약

1613\text{ TFLOPs/s}

로 B200 theoretical peak의 약

71\%

다. arXiv

특히 저자들은 sequence length 4K 이상에서 모든 해당 baseline을 일관되게 앞섰다고 보고한다. arXiv

하지만 더 중요한 문장은 그 다음이다.

논문은 초기 구현 이후 더 최신 cuDNN이 논문에서 사용한 여러 기법을 도입하여 FA4와 비슷한 성능을 내기 시작했다고 적는다. arXiv

따라서 연구의 핵심을

FA4가 cuDNN보다 30% 빠르다

로 기억하면 금방 낡는다.

더 오래가는 지식은

왜 병목이 exp와 shared memory로 이동했으며, 그 병목을 어떤 구조로 제거했는가

다.

18

16. GQA와 FlashAttention은 서로 다른 질문에 답한다

10월 1일 배운 GQA를 연결하자.

GQA는 주로

H_{kv}

를 줄여 KV cache capacity와 decode memory bandwidth를 낮춘다.

반면 FlashAttention은 주어진 \(Q,K,V\)에 대해 attention을 어떤 tile 순서와 memory hierarchy에서 계산할지를 최적화한다.

단순화하면

\boxed{
\text{GQA}:
\text{무엇을 얼마나 저장하는가}
}
\boxed{
\text{FlashAttention}:
\text{필요한 계산을 어떻게 이동·배치·중첩하는가}
}

다.

둘은 경쟁관계가 아니다.

실제 LLM은 GQA와 FlashAttention을 동시에 사용할 수 있다.

19

17. Speculative decoding과도 해결하는 층이 다르다

9월 28일의 speculative decoding은

\text{autoregressive serial steps}

를 줄이려 했다.

FlashAttention은

\text{한 attention operation 내부}

를 빠르게 만든다.

LLM latency를 아주 거칠게

T_{\text{total}}
=
T_{\text{prefill}}
+
T_{\text{decode-attn}}
+
T_{\text{decode-other}}

라 하면,

FlashAttention은 prefill과 attention kernel,

GQA는 KV memory/bandwidth,

speculative decoding은 serial decode step

을 각각 다른 방향에서 줄인다.

좋은 시스템 최적화는 단일 기술 하나가 아니라 서로 다른 병목층을 겹쳐 최적화하는 것이다.

20

18. 2026년의 또 다른 흐름: 최고성능과 개발 유연성을 다시 합친다

FA4는 CuTe-DSL이라는 Python embedded DSL로 구현됐고, 논문은 기존 C++ template 기반 방식보다 20~30배 빠른 compile time을 보고한다. MLSys Proceedings

2026-03-05 PyTorch는 FlexAttention에 FA4 backend를 통합했다고 발표했다. 사용자 정의 score modification과 block sparsity를 FA4 pipeline 안에서 사용할 수 있게 했으며, compute-bound workload에서 기존 Triton backend 대비 1.2~3.2배의 성능 개선을 보고했다. PyTorch

이 흐름은 중요하다.

예전 trade-off는

\text{유연한 high-level code}
\quad\text{vs}\quad
\text{빠른 low-level kernel}

이었다.

최근의 목표는 compiler와 DSL을 이용해

\boxed{
\text{유연한 API}
+
\text{hardware-specific fast path}
}

를 동시에 얻는 것이다.

즉 AI systems의 또 다른 희소자원은 GPU뿐 아니라 고성능 kernel을 개발·컴파일·유지하는 엔지니어링 시간이다.

21

19. 반대 관점과 한계

FA4의 설계를 “미래 GPU에서도 그대로 최적”이라고 보면 안 된다. 논문 자체가 Blackwell 세대의 자원비율에 맞춰 설계됐다. GPU 세대가 바뀌어 SFU나 shared-memory bandwidth가 다시 크게 증가하면 병목은 또 이동할 수 있다. arXiv

또 FlashAttention은 \(N^2\) attention matrix를 저장하지 않지만 dense attention의 모든 Query-Key pair 계산은 여전히 필요하다.

따라서

\boxed{
O(N)\text{ intermediate memory}
\neq
O(N)\text{ arithmetic}
}

이다.

매우 긴 context에서는 \(O(N^2d)\) compute 자체가 다시 중요해진다.

또한 1613 TFLOPs/s는 attention kernel 성능이다. 실제 end-to-end LLM에서는 MLP, communication, KV cache, scheduler, sampling, interconnect 등이 전체 throughput을 제한할 수 있다.

22

20. 시스템 렌즈: 병목은 사라지는 것이 아니라 이동한다

FlashAttention의 발전사를 보면 시스템 최적화의 전형적인 feedback loop가 보인다.

처음에는

N^2\text{ HBM materialization}

이 병목이었다.

그걸 줄이고 나니

\text{parallelism과 occupancy}

가 보였다.

Hopper에서는

\text{memory movement와 MMA overlap}

이 중요해졌다.

Blackwell에서는 Tensor Core가 더 빨라지자

\text{exp와 shared-memory traffic}

이 새 병목이 됐다.

즉

\boxed{
\text{병목을 제거하면 다음 병목의 상대적 중요도가 커진다.}
}

23

21. 경제학 렌즈: 자원의 절대량보다 상대적 희소성이 중요하다

GPU도 여러 생산요소의 묶음이다.

Tensor FLOPs, HBM bandwidth, shared-memory bandwidth, SFU throughput, register/TMEM capacity, interconnect, engineering time이 함께 생산을 만든다.

Tensor Core만 크게 늘어나면 Tensor FLOPs는 상대적으로 풍부해진다.

그러면 늘지 않은

\text{SFU}

나

\text{memory bandwidth}

의 shadow price가 올라간다.

공장에서 절단기만 두 배 들이고 포장라인은 그대로 두는 것과 같다.

전체생산량은 절단기의 peak보다 가장 희소한 보완재에 의해 정해진다.

24

22. 제약이론 렌즈: 가장 빠른 stage가 아니라 가장 느린 stage가 throughput을 결정한다

파이프라인이

\text{matmul}
\rightarrow
\text{softmax}
\rightarrow
\text{matmul}

이라면 matmul 하나를 무한히 빠르게 해도 softmax가 그대로면 전체 속도는 제한된다.

FA4가 하는 일은 두 가지다.

첫째, bottleneck 자체를 줄인다.

둘째, 줄이기 어려운 bottleneck을 다른 작업과 시간적으로 overlap한다.

시스템 성능에서 중요한 것은

\boxed{
\text{각 stage의 peak 성능}
}

보다

\boxed{
\text{pipeline balance와 idle time}
}

인 경우가 많다.

25

23. Goodhart 렌즈: TFLOPs가 목적이 되면 무엇을 놓치는가

Kernel 연구에서는 TFLOPs/s가 편리한 KPI다.

하지만 실제 서비스의 목적은

\text{tokens/s}
\text{time-to-first-token}
\text{inter-token latency}
\text{GPU당 동시 사용자}
\text{energy/token}
\text{원가/token}

일 수 있다.

FA4의 71% peak utilization은 매우 유의미한 engineering result지만

71\%\text{ TFLOPs}
\Rightarrow
71\%\text{ end-to-end 개선}

은 아니다.

항상

\boxed{
\text{최적화한 지표와 실제 목적함수가 같은가?}
}

를 확인해야 한다.

26

24. 산업·투자 렌즈로 확장하면

이 원리는 AI 인프라 병목을 볼 때도 유용하다.

GPU compute가 빠르게 늘면 그에 맞춰

HBM bandwidth,

network fabric,

optical interconnect,

power delivery,

cooling,

storage throughput

도 충분히 늘어야 한다.

하나가 뒤처지면 그 부품의 상대적 희소성이 커진다.

따라서 기술적으로는

\boxed{
\text{가장 빠르게 성장한 자원보다
가장 느리게 따라오는 보완재를 찾아보는 것}
}

이 좋은 탐색법이다.

다만 투자판단에서는 기술적 병목만으로 충분하지 않다. 공급증설 속도, 경쟁구조, 고객 집중도, 가격결정력, 자본집약도까지 별도로 봐야 한다.

27

오늘 기억할 한 문장

\boxed{
\text{하드웨어 최적화에서 중요한 것은
가장 빠른 유닛의 peak가 아니라
전체 pipeline의 가장 느린 보완재와
그 자원을 얼마나 겹쳐 사용할 수 있는가이다.}
}

FlashAttention의 역사를 압축하면

\text{HBM I/O}
\rightarrow
\text{occupancy}
\rightarrow
\text{async overlap}
\rightarrow
\text{exp / shared-memory bottleneck}

으로 병목이 이동해 왔다.

그리고 가장 일반적인 시스템 교훈은 이것이다.

\boxed{
\text{현재 제약을 해결했을 때
다음 제약이 무엇이 될지를 미리 보는 것이 시스템 사고다.}
}

B200 forward tile에서

2{,}097{,}152.

1024

Q3.

한 엔지니어가 말한다.

“FlashAttention은 memory를 \(O(N^2)\)에서 \(O(N)\)으로 줄였으니 long-context attention도 이제 \(O(N)\)이다.”

왜 틀렸는가?

다음 세 가지를 구분해서 설명하라.

\text{intermediate-memory footprint}
\text{HBM I/O}
\text{arithmetic compute}
해설 보기 +

문제 3에서 FlashAttention이 없애는 핵심은 \(N\times N\) intermediate를 HBM에 저장하는 것이다.

그래서 intermediate memory footprint와 HBM traffic은 크게 줄어든다.

}

다.
