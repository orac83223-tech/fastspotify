02

핵심 질문과 결론

핵심 질문: 읽기가 압도적으로 많은 자료구조에서 reader-writer lock이나 reference count를 쓰면 왜 확장성이 나빠질 수 있을까? Linux의 RCU(Read-Copy Update)는 어떻게 reader가 거의 공유 상태를 수정하지 않게 하면서도, writer가 객체를 삭제한 뒤 use-after-free를 피할 수 있을까? 그리고 “grace period가 끝났다”는 말은 정확히 어떤 reader들이 끝났다는 뜻일까?

결론: RCU의 핵심은 “lock-free list” 자체가 아니라 삭제(removal)와 메모리 회수(reclamation)를 시간적으로 분리하는 것이다. Writer는 먼저 자료구조에서 옛 객체를 끊고 새 버전을 publish한다. 하지만 그 옛 객체를 즉시 free하지 않는다. 삭제 이전부터 실행 중이던 reader들이 모두 끝나는 grace period를 기다린 뒤에야 reclaim한다. Reader가 매 접근마다 shared reference counter를 올리고 내리지 않아도 되므로 read-mostly workload에서 매우 빠르고 확장성이 좋다. 대신 비용은 writer 쪽의 지연과 미회수 메모리로 이동한다. McKenney의 최신 공개판도 RCU의 핵심을 publish-subscribe, pre-existing reader 대기, 여러 버전 유지라는 세 축으로 설명한다. Kernel

1. 문제의 본질은 “삭제”가 아니라 “언제 free할 것인가”다

다음 연결 리스트를 생각하자.

A → B → C

Reader \(R_1\)이 B를 읽고 있는 순간 writer \(W\)가 B를 삭제한다고 하자. 단순히 A.next = C를 수행한 뒤 곧바로 free(B)를 호출하면 위험하다. \(R_1\)은 이미 B의 주소를 로컬 레지스터나 스택에 들고 있을 수 있기 때문이다. 자료구조에서는 B가 사라졌지만, \(R_1\)에게는 아직 살아 있는 참조다.

여기서 두 사건을 분리해야 한다.

논리적 삭제(removal)는 새 reader가 더 이상 B를 찾지 못하게 만드는 것이고, 물리적 회수(reclamation)는 B의 메모리를 allocator에 돌려주는 것이다.

전통적인 lock은 흔히 둘을 하나의 임계구역 안에서 처리한다. RCU는 이 둘을 분리한다. Linux 커널 문서도 RCU update를 removal과 reclamation으로 나누며, reclamation은 기존 reader가 더 이상 제거된 객체를 참조하지 않게 된 뒤에만 수행해야 한다고 설명한다. 리눅스 커널 아카이브

2. RCU의 세 동작: publish, remove, reclaim

RCU를 가장 단순하게 보면 세 단계다.

Writer는 새 객체를 완전히 초기화하고 새 pointer를 publish한다. 그다음 옛 객체가 자료구조에서 더 이상 reachable하지 않도록 remove한다. 마지막으로 옛 객체를 볼 수 있었던 기존 reader들이 모두 끝난 뒤 reclaim한다.

핵심은 reader를 멈추는 것이 아니라 옛 버전을 잠시 남겨 두는 것이다. 최신 perfbook은 RCU-protected linked structure에서 새 버전 publish, pre-existing reader 대기, 여러 버전 유지가 각각 insertion, deletion, concurrent traversal을 가능하게 한다고 설명한다. Kernel

이 발상은 데이터베이스의 MVCC와 매우 비슷하다. Writer가 새 버전을 만들더라도 옛 transaction이 옛 버전을 보고 있다면 그 버전을 즉시 지우지 않는다. “현재 보이는 버전”과 “아직 누군가가 참조 중인 버전”은 다를 수 있다.

05

3. Grace period를 수학적으로 정의해보자

각 reader \(i\)의 RCU read-side critical section을 시간구간

I_i=[s_i,e_i]

라고 하자. 어떤 grace period를

G=[g_s,g_e]

라고 하자.

RCU의 핵심 보장을 단순화하면

s_i < g_s < e_i
\quad\Longrightarrow\quad
e_i < g_e

로 쓸 수 있다.

즉 grace period가 시작될 때 이미 진행 중이던 reader는 grace period가 끝나기 전에 반드시 종료해야 한다. 반대로 grace period 시작 이후에 들어온 reader는 그 grace period가 끝날 때까지 반드시 종료할 필요가 없다.

McKenney의 최신판은 이 점을 명시적으로 설명한다. 어떤 read-side critical section이 grace period 시작 전에 일부라도 실행됐다면 그 critical section 전체가 grace period 종료 전에 끝나야 하지만, grace period가 시작된 뒤에 들어온 reader는 grace period 전체와 겹쳐도 될 수 있다. Kernel

이것이 RCU에서 가장 헷갈리는 부분이다.

Grace period는 “모든 reader가 없어질 때까지” 기다리는 시간이 아니다.

더 정확히는

old version을 볼 가능성이 있었던 reader 세대가 빠져나갈 때까지 기다리는 시간이다.

06

4. 타임라인으로 보면 직관이 생긴다

다음 순서를 보자.

t0  R1이 B를 읽기 시작
t1  W가 A.next를 C로 바꿔 B를 제거
t2  grace period 시작
t3  R2가 새로 읽기 시작
t4  R2는 A → C만 봄
t5  R1 종료
t6  grace period 종료
t7  free(B)

\(R_2\)가 \(t_6\) 이후까지 실행 중이어도 B의 reclamation에는 문제가 없다. \(R_2\)는 removal 이후에 시작했기 때문에 정상적인 traversal으로 B를 획득할 수 없기 때문이다.

이 점은 epoch-based reclamation에서도 반복된다. 객체의 생존은 “현재 reachable한가?”만으로 결정되지 않고 과거 epoch의 관찰자가 아직 살아 있는가?까지 고려해야 한다.

07

5. 왜 reader-writer lock보다 빠를 수 있는가

Reader-writer lock도 여러 reader를 동시에 허용한다. 그런데 reader 진입·종료 때마다 shared lock state를 수정한다면 많은 CPU가 같은 cache line을 건드릴 수 있다.

[교육용 계산] 초당 1천만 번 lookup이 발생하고, 각 lookup이 shared reader count에 atomic increment/decrement를 한 번씩 한다고 하자.

10^7 \times 2
=
2\times10^7

즉 초당 2천만 번의 shared atomic RMW가 생긴다.

이 숫자는 특정 커널의 측정값이 아니라 구조를 이해하기 위한 단순화다. 핵심은 core 수가 늘수록 같은 cache line의 ownership 이동과 coherence traffic이 병목이 될 수 있다는 점이다.

RCU는 reader hot path에서 이런 shared write를 최대한 없애는 방향으로 설계된다. 최신 perfbook은 일부 구성, 특히 CONFIG_PREEMPT=n에서 RCU read-side primitive의 overhead가 사실상 0이 될 수 있다고 설명한다. 일반적인 preemptible kernel에서 항상 문자 그대로 0이라는 뜻은 아니며, 중요한 것은 read path의 shared synchronization 비용을 극단적으로 낮추는 것이다. Kernel

08

6. 하지만 RCU는 “아무 동기화도 없다”는 뜻이 아니다

다음 writer를 생각하자.

new->x = 10;
new->y = 20;
global = new;

CPU와 compiler가 reorder할 수 있다면 reader가 새 global pointer는 봤는데 x, y 초기화는 아직 보지 못하는 상황을 피해야 한다.

그래서 Linux RCU는 대표적으로 rcu_assign_pointer()와 rcu_dereference()를 제공한다. 최신 perfbook도 이 두 API를 새 객체를 publish하고 읽는 핵심 메커니즘으로 설명한다. Kernel

개념적으로 writer에서는

\text{initialize(new)}
\prec
\text{publish(new)}

이라는 ordering이 필요하다.

따라서 RCU를

“reader가 lock을 안 잡으니 그냥 pointer를 읽어도 된다”

라고 이해하면 위험하다.

RCU는 동기화의 부재가 아니라 reader 쪽 동기화 비용을 매우 작게 만든 설계다.

7. 가장 작은 의사코드

// reader
rcu_read_lock();

p = rcu_dereference(global_ptr);
value = p->value;

rcu_read_unlock();


// writer
new = malloc(...);
new->value = 42;

old = rcu_replace_pointer(global_ptr, new, ...);

// old를 지금 free하면 안 됨
synchronize_rcu();

free(old);

여기서 synchronize_rcu()의 의미가 중요하다.

이 함수는 “현재 실행 중인 모든 reader가 사라질 때까지”를 뜻하지 않는다. 호출 이전부터 존재해 old를 볼 가능성이 있던 reader가 끝났음을 보장하는 경계에 가깝다.

업데이트 경로를 block시키고 싶지 않다면 call_rcu() 같은 callback 방식으로 reclamation을 뒤로 넘길 수도 있다. 현재 Linux API 문서도 call_rcu() callback이 full grace period 이후 실행된다고 설명한다. 커널 문서

10

8. RCU는 lifetime을 보호하지, 임의의 snapshot 일관성을 자동 보장하지 않는다

아주 흔한 오해가 있다.

RCU 보호 아래 있는 객체는 언제나 consistent snapshot으로 보인다.

그렇지 않다.

RCU의 가장 중요한 역할은 reader가 보고 있는 객체가 갑자기 free되지 않게 하는 lifetime protection이다.

예를 들어 동일 객체의 두 필드를 writer가 in-place로

x = 100
y = 200

순서로 바꾸면 reader가 x=100, y=old인 중간 상태를 보는 문제까지 RCU가 자동으로 해결해주지는 않는다.

여러 필드를 일관된 snapshot으로 읽어야 한다면 새 객체를 통째로 구성한 뒤 pointer를 교체하거나, writer lock, sequence lock 같은 다른 기법을 조합해야 한다.

즉 RCU에서는

\boxed{
\text{object lifetime safety}
\neq
\text{arbitrary state consistency}
}

를 분리해서 생각해야 한다.

9. 가장 큰 대가: reclamation debt

RCU reader를 싸게 만든 대가가 사라진 것은 아니다. 비용은 writer와 memory 쪽으로 이동한다.

삭제된 객체는 grace period가 끝날 때까지 메모리에 남아 있어야 한다.

이를 queueing 문제로 볼 수 있다. 단위시간당 retire되는 객체 수를 \(\lambda\), 평균 reclaim 대기시간을 \(W\), 평균 unreclaimed 객체 수를 \(L\)이라 하자.

정상상태 근사에서 Little’s Law를 적용하면

\boxed{L\approx\lambda W}

다.

[교육용 예제]

초당

\lambda=50{,}000

개의 객체가 retire되고 평균 grace-period+callback 대기시간이

W=40ms=0.04s

라면

L\approx50{,}000\times0.04
=2{,}000

개의 객체가 평균적으로 미회수 상태다.

객체 하나가 256 bytes라면

2{,}000\times256
=
512{,}000 \text{ bytes}

즉 약 0.5MB다.

그런데 stalled reader 때문에 평균 대기가 2초로 늘어나면

50{,}000\times2
=
100{,}000

개,

100{,}000\times256
=
25.6MB

가 된다.

실제 RCU는 callback batching, 여러 grace period, bursty workload 때문에 이보다 복잡하지만 방향은 같다.

최신 perfbook은 RCU가 reader가 접근 가능한 객체를 reader 종료 전까지 free할 수 없기 때문에, update를 throttle하지 않으면 memory footprint가 이론적으로 unbounded할 수 있다고 설명한다. Kernel

이것을 reclamation debt라고 생각하면 좋다.

Reader latency를 줄이는 대신 시스템은 “나중에 free해야 할 부채”를 쌓는다.

10. 긴 reader가 왜 위험한가

Read-side critical section이 너무 길어지면 grace period가 늘어날 수 있다.

그러면

grace period 증가
→ callback backlog 증가
→ unreclaimed memory 증가
→ memory pressure 증가
→ reclaim/allocator activity 증가
→ 시스템 jitter 증가

라는 feedback loop가 생길 수 있다.

따라서 reader API가 싸다는 사실과 read-side section을 오래 유지해도 된다는 것은 전혀 다른 이야기다.

빠른 read path는 긴 critical section을 정당화하지 않는다.

13

11. reference counting과는 무엇이 다른가

Reference counting은 reader가 객체를 잡을 때마다

refcount++

놓을 때

refcount--

를 수행하고 0이 되면 reclaim한다.

장점은 객체별 생존기간을 비교적 정밀하게 추적할 수 있다는 점이다. 대신 reader마다 shared state update가 생긴다.

RCU는 반대로 reader가

“나는 객체 X를 보고 있다”

라고 객체별로 신고하지 않는다.

대신

“이 reader generation이 끝날 때까지 그 이전에 retire된 객체를 전부 살려 둔다”

에 가깝다.

그래서 reader는 싸지만 memory retention이 더 거칠다.

최신 perfbook도 짧은 참조에는 RCU를 쓰고, 오랫동안 보유해야 하는 일부 객체에는 reference count를 결합하는 패턴을 설명한다. Kernel

즉 둘은 반드시 경쟁 기술이 아니다.

14

12. hazard pointer와 비교하면 철학이 더 잘 보인다

Hazard pointer는 reader가

“나는 지금 객체 X를 사용 중이다”

라는 pointer를 공개한다.

Writer는 reclaim 전에 hazard slot을 훑어 X가 보호 중인지 확인한다.

이를 경제적으로 표현하면 다음과 같다.

Hazard pointer: reader가 보호 필요성을 개별 신고한다.

RCU: 시스템이 reader 세대 전체에 일괄 유예기간을 준다.

Hazard pointer는 미회수 객체 수를 더 엄격하게 제한할 수 있지만 reader-side publication과 retry가 필요할 수 있다. RCU는 reader path가 더 싸지만 retired object가 더 많이 쌓일 수 있다.

C++의 RCU 표준화 제안 P2545R4도 reference counting, hazard pointer, RCU를 reader scalability, unreclaimed-object bound, traversal retry, reclamation latency 측면에서 비교한다. Open Standards

13. 2024~2026의 흐름 ①: RCU API도 “인간이 덜 틀리게” 진화한다

Paul McKenney가 기고한 “The RCU API, 2024 edition”에는 guard(rcu)()와 scoped_guard() 같은 read-side guard가 소개된다. 이들은 scope 종료 시 critical section을 자동으로 끝내도록 해 rcu_read_unlock() 누락 같은 실수를 줄인다. LWN.net

즉 low-level kernel concurrency에서도

\text{resource lifetime}
=
\text{lexical scope}

라는 RAII 계열의 아이디어가 들어온다.

이것은 단순 성능 최적화가 아니라 API가 인간 오류를 줄이도록 설계되는 방향이다.

14. 2024~2026의 흐름 ②: latency와 energy 사이에서도 RCU가 조정된다

같은 2024 RCU API 설명에는 lazy RCU callback이 나온다. 배터리 기반 Android·ChromeOS 환경에서 거의 idle한 시스템이 callback 때문에 grace period를 자주 시작하면 CPU wakeup이 늘기 때문에, 일부 call_rcu() callback을 늦추고 batch해 wakeup 수를 줄이는 방식이다. 해당 글은 테스트에서 energy efficiency가 10%를 훨씬 넘게 개선됐다고 보고한다. 반대로 지연을 허용할 수 없는 callback을 위해 call_rcu_hurry()도 제공된다. LWN.net

즉 여기서도 trade-off는

\boxed{
\text{reclamation latency}
\leftrightarrow
\text{energy efficiency}
}

다.

RCU는 단순 synchronization primitive가 아니라 scheduler, power management, callback placement까지 이어지는 시스템 메커니즘이다.

17

15. 2023~2026의 흐름 ③: Linux 전용 지식에서 C++ safe reclamation으로

WG21의 P2545R4 “Read-Copy Update (RCU)”는 2023-03-08 문서로, RCU를 C++26의 safe-reclamation facility로 제안했다. 문서는 <rcu> API와 rcu_synchronize(), rcu_retire() 같은 기능을 일반 C++ 라이브러리 수준으로 올리는 방향을 설명한다. Open Standards

현재 cppreference의 C++26 library 목록에도 <rcu>가 safe-reclamation 영역의 새 기능으로 정리되어 있다. Cppreference

이 변화의 의미는 크다.

RCU가

Linux kernel 내부 전문가만 쓰는 특수 synchronization

에서

일반 C++ concurrent data structure의 memory reclamation primitive

로 이동하고 있는 것이다.

그리고 표준화가 보여주는 또 하나의 현실은, 알고리즘 자체보다 더 어려운 것이 누가 언제 reader인지, 무엇을 retire했는지, 언제 reclaim해도 되는지를 사용자가 틀리지 않게 표현하는 API 계약이라는 점이다.

18

16. RCU가 좋은 경우와 나쁜 경우

RCU는 읽기가 압도적으로 많고 update가 드문 자료구조, 짧은 reader critical section, pointer 기반 lookup/traversal, reader latency와 scalability가 중요하고 old version을 잠시 보존할 memory 여유가 있는 경우에 강하다.

반대로 update가 매우 많거나, reader가 오래 block할 수 있거나, 즉시 reclamation이 중요하거나, 여러 필드를 강하게 일관된 snapshot으로 읽어야 하거나, 단순 lock으로 충분한 작은 코드에서는 신중해야 한다.

따라서

\boxed{
\text{RCU가 더 고급 기술이므로 항상 더 좋다}
}

는 틀린 결론이다.

좋은 synchronization은 workload의 read/write 비율, critical-section 길이, memory budget, latency SLO에 맞아야 한다.

19

17. 다학제 렌즈 ①: MVCC와 같은 “시간으로 푸는 동시성”

Lock은 접근을 막는다.

지금 이 객체는 내가 사용하니 너는 기다려.

RCU와 MVCC는 시간을 쓴다.

너는 새 버전을 보고, 나는 아직 옛 버전을 보겠다. 옛 관찰자가 사라지면 옛 버전을 치운다.

즉 동시성 문제를

\text{누가 접근할 권리가 있는가}

에서

\text{어떤 버전이 언제까지 살아 있어야 하는가}

로 바꾼다.

이 관점으로 보면 database snapshot, copy-on-write filesystem, epoch reclamation, rolling configuration change가 같은 계열의 문제로 보인다.

20

18. 다학제 렌즈 ②: reader의 비용을 writer와 memory에 이전하는 경제학

Synchronization 비용은 없어지지 않는다.

RCU는 비용의 귀착을 바꾼다.

Reader는 shared atomic과 대기를 줄이고, Writer는 copy/update, grace-period tracking, deferred free를 부담하며, Memory는 old version을 임시로 보유한다.

즉

\boxed{
\text{reader latency를 낮추기 위해 writer latency와 memory를 지불한다}
}

는 구조다.

이것은 시스템 전반에서 반복된다.

CDN은 origin 부하를 cache memory로 바꾸고, database index는 write cost와 storage를 지불해 read latency를 줄이며, speculative decoding은 추가 compute를 써서 serial latency를 줄인다.

좋은 최적화는 비용을 없애는 것이 아니라 더 싼 자원으로 비용을 이전하는 것인 경우가 많다.

21

19. 다학제 렌즈 ③: 안전한 변경관리와도 같은 구조다

운영 중인 프로세스를 새 규정으로 바꾼다고 하자.

신규 업무는 즉시 새 규정을 적용할 수 있다. 하지만 이미 진행 중인 건은 옛 규정을 참조하고 있을 수 있다.

안전한 전환은 보통

1. 신규 진입을 새 버전으로 전환
2. 기존 진행 건의 종료를 기다림
3. 옛 규정·시스템을 폐기

순서다.

이것이 정확히

\text{remove}
\rightarrow
\text{grace period}
\rightarrow
\text{reclaim}

구조다.

변경의 효력 발생 시점과 기존 참조의 소멸 시점을 분리하는 것이 안전한 전환의 핵심이다.

22

오늘 기억할 한 문장

\boxed{
\text{RCU는 삭제를 늦추는 기술이 아니라, “보이지 않게 만드는 시점”과 “메모리를 회수해도 되는 시점”을 분리하는 기술이다.}
}

그리고 grace period의 핵심은

\boxed{
\text{모든 reader를 기다리는 것이 아니라 old version을 볼 수 있었던 reader 세대를 기다린다.}
}

이 관점을 이해하면 RCU뿐 아니라 MVCC, epoch-based reclamation, copy-on-write, rolling configuration change도 하나의 공통 패턴으로 보이기 시작한다.

PAUSE & REFLECT

잠깐, 내 언어로 설명해 보기

Q1.

다음 reader가 있다.

R_1=[1,8],\quad
R_2=[4,5],\quad
R_3=[7,12].

Writer가 시각 6에 old object를 자료구조에서 제거하고 동시에 grace period를 시작한다고 하자.

1. grace period 종료를 위해 반드시 기다려야 하는 reader는 누구인가?
2. \(R_3\)가 시각 12까지 실행되더라도 old object를 시각 9에 reclaim할 수 있는 조건은 무엇인가?
3. “grace period는 모든 현재 reader가 종료될 때까지 기다린다”가 왜 부정확한가?

해설 보기 +

시각 6에 grace period가 시작된다.

\(R_1=[1,8]\)은 이미 실행 중이므로 반드시 기다려야 한다.

\(R_2=[4,5]\)는 grace period 시작 전에 이미 끝났으므로 기다릴 필요가 없다.

\(R_3=[7,12]\)는 grace period 시작 뒤 들어왔으므로, old object가 시각 6에 정상 traversal에서 이미 제거되었다면 old object reclamation을 위해 기다릴 필요가 없다.

따라서 \(R_1\)이 시각 8에 끝난 뒤 필요한 ordering과 grace-period 조건이 충족됐다면 시각 9 reclaim이 가능하다.

핵심은 모든 reader가 아니라 old version을 볼 수 있었던 pre-existing reader다.

Q2.

초당 retire rate가

\lambda=80{,}000

objects/s이고 평균 reclamation delay가

W=25ms

라고 하자.

1. Little’s Law 근사로 평균 unreclaimed object 수를 구하라.
2. 객체당 크기가 512 bytes라면 평균 미회수 memory를 계산하라.
3. stalled reader 때문에 \(W=1.5s\)로 증가하면 미회수 memory는 얼마인가?

해설 보기 +
L=\lambda W
=
80{,}000\times0.025
=
2{,}000.

평균 2,000 objects다.

메모리는

2{,}000\times512
=
1{,}024{,}000\text{ bytes}

즉 약 1.0MB다.

\(W=1.5s\)가 되면

L=80{,}000\times1.5
=
120{,}000

objects이고,

120{,}000\times512
=
61{,}440{,}000\text{ bytes}

즉 약 61.4MB다.

이 예제는 reader stall이 단순 latency 문제가 아니라 memory backlog 문제라는 것을 보여준다.

Q3.

읽기 1천만 회/s, update 1천 회/s인 자료구조가 있다.

Reference-count 방식에서 lookup마다 shared atomic increment/decrement가 각각 한 번씩 발생한다고 단순화하자.

1. reader 때문에 발생하는 shared atomic RMW 횟수는 초당 몇 회인가?
2. RCU가 이 reader-side shared RMW를 대부분 제거한다면 무엇을 새로 부담해야 하는가?
3. “RCU는 공짜로 빠르다”가 왜 틀린 설명인가?

해설 보기 +

Lookup당 atomic RMW가 2회이므로

10{,}000{,}000\times2
=
20{,}000{,}000

즉 초당 2천만 회다.

RCU는 이를 줄이는 대신 writer가 old/new version 관리, grace-period 추적, deferred reclamation, callback backlog를 부담한다. Memory도 old version을 잠시 유지해야 한다.

즉 비용이 제거된 것이 아니라

\boxed{
\text{reader shared synchronization}
\rightarrow
\text{writer/reclaimer + memory}
}

로 이동한 것이다.
